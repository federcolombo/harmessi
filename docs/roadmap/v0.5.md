# Harmessi v0.5 — Multi-Provider & Evaluation

> Estado: PLANIFICADA. Revisar el alcance al cerrar v0.4 antes de ejecutarla.

## Objetivo

Hacer que Harmessi deje de depender de un único proveedor y pueda medir objetivamente el comportamiento de distintas configuraciones de agentes/modelos antes de tomar decisiones de routing o fallback.

La secuencia de la versión es deliberada:

`adapters → evals → routing → fallback/handoffs → hardening`

Principios:

- subscription-first;
- CLIs nativas de cada proveedor;
- core neutral;
- adapters finos;
- sin frontend/TUI propio;
- evals separados de tests;
- routing basado en evidencia, no intuición;
- fallback automático solo por disponibilidad/cuota;
- nunca fallback automático por error semántico, error de código o desacuerdo metodológico.

## Change 0 — multi-provider-adapters

**Estado:** DONE. Entregado: contrato core neutral (`tools/providers/core.py`) + 4 adapters finos
(Claude Code, Codex CLI, Gemini CLI, Grok CLI) con detección de disponibilidad, capacidades e
invocación vía subprocess, wiring en `harmessi providers list`. Solo `ClaudeCodeAdapter` verificado
contra un binario real (`claude -p` real, respuesta JSON parseada correctamente); los otros 3
quedan best-effort, sin CLI instalada en este entorno. 1 ronda de reviewer (4 hallazgos
importantes corregidos: manejo de excepciones en `invoke()`, heurística de clasificación de
errores de disponibilidad, test acoplado a proceso real, contrato `role`/`translate_role()`
documentado como placeholder para Change 2).

Objetivo:

crear adapters finos para ejecutar Harmessi mediante CLIs nativas de múltiples proveedores sin contaminar el core.

Proveedores objetivo:

- Claude Code;
- Codex CLI;
- Gemini / Antigravity;
- Grok CLI.

Principios:

- autenticación y suscripción administradas por el proveedor;
- no usar APIs por defecto cuando la CLI/subscripción sea suficiente;
- no crear frontend/TUI propio;
- no duplicar lógica metodológica en adapters;
- mantener contratos neutrales en el core;
- handoffs explícitos;
- degradación clara cuando un proveedor no esté disponible.

El adapter debe resolver solo lo necesario para:

- invocación;
- capacidades disponibles;
- identificación de provider/model cuando sea posible;
- traducción mínima de roles/handoffs;
- errores de disponibilidad/cuota.

No implementar routing inteligente todavía.

## Change 1 — harmessi-bench

**Estado:** DONE. Entregado: framework de evals separado de los tests (`tools/harmessi_bench/`:
core, scenarios, runner, storage, compare) y CLI propio (`python -m tools.harmessi_bench.cli`).
Verificado con una corrida real end-to-end contra `claude_code` (3/3 escenarios de ejemplo
pasaron) y un `compare` real sobre esa misma corrida. Scoring puramente determinista
(contains/regex/exact), sin LLM-as-judge. 1 ronda de reviewer (4 hallazgos importantes + 2 menores
corregidos: manejo de errores en `compare`/`cli`, docstring inconsistente, flag interno expuesto en
`--help`).

Objetivo:

crear un framework de evals separado de los tests deterministas.

Debe permitir:

- escenarios reproducibles;
- evaluar Lead/agentes/harness;
- medir regresiones de comportamiento;
- comparar configuraciones/provider/model;
- registrar resultados comparables entre versiones;
- separar correctness determinista de calidad agentic.

Principio:

`tests → verifican contratos deterministas`

`evals → miden calidad de comportamiento`

No convertir los tests unitarios actuales en evals.

No diseñar todavía un leaderboard público complejo.

## Change 2 — provider-routing

**Estado:** DONE. Entregado: resolutor declarativo de routing (`tools/routing/`:
`RoutingRule`/`RoutingPolicy`/`RoutingDecision` + `resolve()` + carga/validación de política
opcional desde `.harmessi/routing.json`) y wiring en `harmessi routing show|resolve`, incluyendo
`--check-availability` compuesto con `tools.providers.list_providers()` de Change 0. Sin
integración automática con resultados de `harmessi-bench` (deliberado, sin optimización
automática). 1 ronda de reviewer (1 hallazgo importante corregido: validación de forma ante JSON
mal formado).

Objetivo:

seleccionar provider/model de forma explícita y gobernada según rol, tarea y esfuerzo.

Dimensiones candidatas:

- rol;
- tipo de tarea;
- provider;
- model;
- effort/thinking cuando el proveedor lo soporte;
- restricciones de disponibilidad;
- resultados de evals.

El routing debe ser:

- configurable;
- trazable;
- determinista cuando exista una regla explícita;
- neutral al proveedor en el core.

No inventar una optimización automática basada en costos/tokens no observables.

Para cambios de alto riesgo, preferir reviewer de familia de modelo distinta al writer cuando sea viable y esté configurado.

## Change 3 — fallback-and-handoffs

**Estado:** DONE. Entregado: motor de fallback técnico (`tools/fallback/core.py`:
`is_fallback_eligible`/`invoke_with_fallback`/`FallbackOutcome`) que solo reintenta ante
indisponibilidad real, nunca ante error semántico o de código, y persistencia de contexto de
handoff SDD (`tools/fallback/handoff.py`). Verificado con un smoke real de fallback genuino
(`codex` no instalado → fallback automático a `claude_code`, que respondió de verdad). 1 ronda de
reviewer, que confirmó sin excepciones la garantía crítica de elegibilidad (1 hallazgo importante
corregido: colisión silenciosa de `save_handoff`).

Objetivo:

hacer robusta la continuidad entre proveedores sin esconder errores reales.

Fallback automático permitido solo por:

- quota;
- availability;
- proveedor temporalmente inaccesible.

Fallback automático prohibido por:

- error semántico;
- error de código;
- test fallido;
- disagreement metodológico;
- reviewer finding;
- mala calidad de output.

Handoffs:

- explícitos;
- con contexto mínimo suficiente;
- sin duplicar auditorías;
- sin reiniciar trabajo ya completado;
- preservando SDD, estado del Change y trazabilidad.

## Change 4 — cross-provider-hardening

**Estado:** DONE. Entregado: 4 suites de test nuevas (neutralidad estructural del core vía AST,
paridad de contrato de los 4 adapters, paridad de fallback y de routing entre los 4 `provider_id`),
sin tocar ningún código de producción. Confirmó genuinamente que la paridad entre providers no es
decorativa y que el core no depende de literales de Claude. Cobertura de smoke documentada
honestamente: `claude_code` real (Changes 0/1/3), `codex`/`gemini`/`grok` N/A por ausencia de CLI en
este entorno (detección limpia, sin fabricar disponibilidad). 1 ronda de reviewer (1 hallazgo
importante corregido: asimetría de cobertura del test de opacidad de `role`).

Objetivo:

verificar que los contratos de Harmessi se comporten de forma coherente entre los proveedores soportados.

Validaciones:

- smoke tests por adapter;
- handoffs;
- errores de cuota/disponibilidad;
- routing;
- compatibilidad de roles;
- one-writer;
- bounded remediation;
- outputs esperados;
- ausencia de dependencia accidental de Claude en el core neutral.

No agregar features nuevas en este Change salvo fixes necesarios para compatibilidad real.
