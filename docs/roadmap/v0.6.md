## Objetivo

Construir un Reporting Core gobernado, y usar EDA como su primer profile, sin acoplar Harmessi a
un dominio, empresa, dataset o librería gráfica particular.

Harmessi no debe copiar el EDA de un proyecto particular: debe generalizar contratos reutilizables
de reporting gobernado.

Flujo conceptual:

```
Proyecto / Notebook
        ↓
Report objects
        ↓
Governance
        ↓
Evidence / Validation
        ↓
Design System
        ↓
Renderer
        ↓
report.html + manifest.json + insights.json + artifacts/
```

Principio operativo (heredado, permanente):

> LLM decide lo semántico; el binario calcula y hace cumplir lo determinista.

La secuencia de la versión es deliberada:

`reporting-core → reporting-governance → eda-profile → evidence-and-validation → design-system-and-renderer → hardening`

## Change 0 — reporting-core

Objetivo: definir contratos neutrales de reporting, conceptualmente:

- `Report`;
- `Chapter`;
- `FigureArtifact`;
- `TableArtifact`;
- `Insight`.

Separar dos dimensiones ortogonales, que no deben confundirse entre sí:

`report_kind` (qué tipo de reporte es):
- `eda`;
- `model`;
- `evaluation`;
- `production`.

`decision_scope` (para qué decisiones puede utilizarse):
- `exploratory`;
- `model_valid`;
- `operational`.

El notebook/código del proyecto calcula. Harmessi gobierna, valida, registra y renderiza -- no
duplica el cálculo.

`.ipynb` es el artefacto reproducible de análisis; `.html` es el artefacto de comunicación. El
notebook no debe convertirse en un renderer.

## Change 1 — reporting-governance

Objetivo: generalizar sobre el Reporting Core (no reinventar) las siguientes capacidades:

- output guard;
- destinos permitidos;
- separación `exploratory` ↔ `model_valid`;
- protección de holdout;
- aislamiento read/write;
- outputs sensibles;
- integración con scientific validity ya existente (`tools/dsguard/scientific_validity.py`).

No duplicar sistemas de holdout, hashes o provenance que Harmessi ya tenga (`pathguard`,
`ds_profile`, `dsguard`).

Debe poder impedir mecánicamente que outputs exploratorios alimenten modelado cuando no
corresponda.

## Change 2 — eda-profile

EDA debe ser un profile encima del Reporting Core, no el Reporting Core mismo.

Anatomía metodológica candidata (bloques a evaluar, no a ejecutar incondicionalmente):

- `data_quality`;
- `univariate`;
- `bivariate_target`;
- `multivariate`;
- `temporal`;
- `concentration`;
- `segmentation`;
- `entity_relations`;
- `process_cycles`.

No todo aplica a todos los proyectos. Cada bloque debe quedar explícitamente evaluado, con un
estado equivalente a:

- `required` / `applicable`;
- `not_applicable`;
- `omitted`.

Toda omisión debe llevar `reason`.

Principio: un EDA completo no significa ejecutar todos los análisis posibles; significa decidir
explícitamente cuáles aplican y justificar lo que no se realiza.

No hardcodear en el core: PCA, clustering, RFM, Pareto, cohortes, bootstrap, chi-cuadrado ni
ninguna otra técnica específica. El profile puede conocer familias metodológicas; el proyecto
decide cómo calcularlas.

## Change 3 — report-evidence-and-validation

Objetivo: formalizar manifest, provenance, source hashes, data cutoff, exclusiones, holdout
access, sensibilidad, source notebook/run, insights y referencias de evidencia.

El manifest debe poder registrar, conceptualmente:

- `report_id`;
- `run_id`;
- `report_kind`;
- `decision_scope`;
- `data_cutoff`;
- `git_commit`;
- `harmessi_version`;
- `sources`;
- `hashes`;
- `rows`;
- `min`/`max date`;
- `exclusions`;
- `holdout_access`;
- `sensitive`;
- `generated_at`.

No duplicar capacidades existentes si ya están resueltas por Harmessi.

Reglas deterministas candidatas:

- reporte sin manifest → `FAIL`;
- figure sin backing table → `FAIL`;
- insight sin evidence reference → `FAIL`/`WARN` según contrato;
- fuente inexistente o hash stale → `FAIL`;
- applicability no evaluada en EDA → `WARN`/`FAIL` según diseño;
- flujo `model_valid` leyendo outputs `exploratory` → `FAIL`.

La regla "ningún gráfico sin su tabla de respaldo" debe convertirse en una regla verificable, no
solo editorial.

`Insight` debe separar conceptualmente:

- `technical_claim`;
- `business_claim`;
- `evidence_refs`;
- `population`;
- `time_scope`;
- `claim_type`;
- `uncertainty`.

El renderer muestra el `business_claim`. Lead/metodólogo/reviewer pueden auditar `technical_claim`
+ evidencia.

El binario verifica existencia y coherencia estructural. El LLM evalúa interpretación, causalidad,
adecuación metodológica, y si la conclusión excede la evidencia disponible.

## Change 4 — reporting-design-system-and-html-renderer

Objetivo: incorporar explícitamente un Design System desacoplado del renderer, separando dos
contratos:

**`VisualStyle`**: palette/tokens, typography, spacing, radii, content widths, semantic colors,
tables, cards/panels, callouts, responsive behavior, screen theme, print theme, chart styling,
locale/number formatting.

**`EditorialStyle`** (contrato/configuración, no hardcodeado): locale, audience, tone, explicación
de términos estadísticos/técnicos, contexto comparativo de cifras, estilo de insights,
incertidumbre, recomendaciones solo cuando la evidencia las sostenga. No hardcodear castellano, un
dominio ni un vocabulario particular en el core.

Implementar inicialmente:

- `HarmessiDefaultTheme`, con posibilidad de project theme overrides;
- Plotly como primer y único backend gráfico soportado en v0.6 -- Plotly NO forma parte del
  contrato central, `FigureArtifact` debe permanecer neutral;
- dark theme para pantalla, light theme para impresión;
- HTML self-contained/offline;
- componentes reutilizables: header, report intro, technical sheet, chapter, figures, backing
  tables, method details, insight callout, tabs, conclusion, footer.

Limitación técnica real a considerar: los colores de Plotly quedan materializados en el JSON de la
figura, por lo que el tema de impresión no puede depender únicamente de CSS `@media print` -- debe
existir una estrategia compatible de render screen/print.

Reglas genéricas de chart styling candidatas: título en lenguaje del lector (no nombre del
algoritmo); unidades visibles; denominador/tamaño de grupo junto a tasas; leyendas interpretables;
etiquetas largas sin truncamiento; colores semánticos cuando representan riesgo/estado; tablas
completas aunque el gráfico use top-N; formato locale consistente.

Fuera de alcance de este Change: branding específico de empresas, logos particulares, paletas de
clientes, vocabulario específico de dominio, otras librerías gráficas, editor visual de themes, CSS
framework, servidor web, dashboard interactivo.
