# Harmessi v0.11 — Operational Robustness & Recovery

## Estado

**Candidato a release (`0.11.0`); Changes 0–5 cerrados; Change 6 en curso.** Pasará a «PUBLICADA como v0.11.0 (2026-10-20) — ver
`docs/releases/v0.11.0.md`» solo cuando se publique.

Roadmap congelado por Change 0 `20261016-v011-roadmap-and-operational-audit` (2026-10-16), sobre `main` == `origin/main` == `2e76956`
(`v0.10.0` publicada). Rama de desarrollo `v0.11-dev`, solo local. Cada Change refina sus criterios en su propio SDD.

## Objetivo

Fortalecer el funcionamiento REAL del harness antes de sumar familias nuevas de Data Science.

> Fail explicitly, recover deterministically, preserve evidence.

Prioridades: eliminar degradaciones silenciosas; fail-closed donde corresponde; recovery soportado; integridad operativa; instalación,
upgrades y migraciones sin estados `half old / half new`; atribución y aislamiento entre Changes; contratos listos para una futura
estabilización pública (v1.0). **No es una release de features nuevas.**

## Principios

- `unknown != clean`: un estado desconocido nunca se trata como estado sano.
- Historia append-only: las correcciones se agregan, nunca reescriben.
- `session expiry != lost work`.
- Recuperación soportada y probada, no manual e implícita.
- Sin cambios de hooks, scope o schemas basados solo en tests sintéticos si el defecto depende de un payload real.
- Provider-neutral, source-neutral, subscription-first, local-first; sin acoplamiento nuevo a Claude/Codex/Gemini en el core.
- Se preservan sin reabrir (salvo bug real): Role ≠ Skill ≠ Runtime; un ROL writer con N instancias de ownership disjunto; el Lead no es writer;
  reviewer read-only; subagentes no delegan; notebook writer ≠ notebook execution; LLM decide semántica y el runtime enforcea lo determinista;
  evals ≠ tests; T0/T1; `console_confirmed` no es identidad; scope amendments; guardrails readopt; `domain-modeling`; `GLOSSARY.md` project-owned.

### Change 1 — Git & Scope Fail-Closed Hardening
**Objetivo.** `unknown Git state != clean Git state`.
**Problema.** Ver filas Git de la tabla: un fallo de `git status`/`diff` o un Git ausente puede verse como «sin archivos tocados».
**Scope.** Verificar returncode en todos los usos de `_git` que alimentan decisiones; hallazgo gobernado único (reutilizando
`ALCANCE-GIT-ILEGIBLE` o un código hermano) para Git fallido/no disponible/ref inválida; evaluar ambos lados de rename/copy; `--` antes de refs;
captura de bytes sin universal newlines; documentar los códigos en `verificador.md` y su plantilla.
**Boundaries.** Sin nuevo subcomando Git en la lista blanca; sin cambio de semántica de scope/amendments; sin cambiar el parseo `-z`.
**Dependencias.** Ninguna (tras 0).
**Aceptación.** (a) `git status` con returncode ≠ 0 produce hallazgo, nunca `[]`; (b) ref inválida/borrada y Git ausente producen hallazgo
fail-closed en `validate` y gates; (c) un rename desde una ruta no autorizada se reporta; (d) una ref que empieza con `-` no se interpreta como
opción; (e) un nombre con `\r` conserva el byte; (f) códigos documentados; (g) tests de regresión de v0.10 (Unicode, `-z`) siguen verdes.
**Riesgos.** Falsos bloqueos en entornos sin Git estable → el mensaje debe ser accionable. **Diferido.** Cross-platform CI.

### Change 2 — Decision Ledger Corrections & Integrity
**Objetivo.** Corregir sin reescribir historia.
**Problema.** No existe una vía append-only para corregir un campo (typo, cita, evidencia) sin crear una decisión nueva con aprobación completa.
**Scope.** Acción append-only de corrección con `referencia`, campos corregidos, motivo y aprobación; estado derivado sin almacenar. Naming:
**`decision correct`** (se evita `amend`, ya usado por `scope amend`, que amplía autoridad y exige T1). Auditar e implementar, si falta, la
validación de integridad de lectura (continuidad de `seq`, ids duplicados, referencias colgantes) como hallazgos; schema versionado y lectura
compatible con ledgers v1 existentes.
**Boundaries.** Nunca editar ni borrar líneas; sin cadena criptográfica ni event sourcing genérico; el enum de tipos NO se amplía sin un
consumidor real. **Dependencias.** Ninguna (tras 0). **Aceptación.** (a) una corrección no altera ninguna línea previa (bytes idénticos);
(b) `list/show` muestran valor efectivo y su historia; (c) un ledger v0.10 lee sin migrar; (d) línea corrupta/seq roto → fail-closed en
escritura y hallazgo en lectura; (e) referencia inexistente rechazada; (f) docs de `decision-ledger.md`.
**Riesgos.** Ambigüedad entre `supersede` y `correct` → regla escrita: `correct` no cambia el sentido de la decisión. **Diferido.** Enum de tipos.

### Change 3 — Sessions, Continuations & Recovery
**Objetivo.** `session expiry != lost work`.
**Scope.** Fuente única del default de minutos (hoy triplicado), sin cambiar el valor 90; warning anticipado determinista antes del cierre por
hook; recovery verificable (cierre de sesión vencida + apertura de la siguiente con handoff del estado de tareas); semántica explícita de
esperas T1, tests largos y agentes en background frente al reloj wall-clock; coherencia con `--max-continuaciones` y `ESTADO-AGENTE`.
**Boundaries.** `maxTurns` y 90 sin cambios; si pausar el reloj durante T1 requiere cambiar la semántica wall-clock, se presenta como
decisión material en el SDD. Sin scheduler. **Dependencias.** Ninguna (tras 0). **Aceptación.** (a) un único lugar define el default y un test
falla si reaparece el literal; (b) el warning se emite una vez, antes de bloquear; (c) test de recovery: sesión vencida con tareas abiertas →
nueva sesión retoma sin pérdida de estado en `control.json`; (d) docs de §30 actualizados con evidencia reproducible. **Riesgos.** Interacción con
el hook de presupuesto (cambia un hook: requiere tests de payload y reviewer). **Diferido.** Provider T2.

### Change 4 — Runtime Attribution & Parallel Change Isolation
Dos problemas que comparten superficie (`scope.py`, hooks) pero se resuelven y validan por separado dentro del mismo Change.
**4B — Parallel Changes (determinista, primero).** `ALCANCE-RUTA` no debe fallar por modificaciones legítimas de OTRO Change abierto, y
tampoco ignorar conflictos reales. Regla candidata: una ruta tocada que cae solo en el alcance efectivo de otro Change abierto se reporta
como atribuida a ese Change; una ruta fuera de todos los alcances, o dentro de dos alcances abiertos, sigue siendo hallazgo (conflicto).
Una cadena de enmiendas inválida de otro Change no autoriza nada.
**4A — Runtime attribution (gated por evidencia).** Primero se captura evidencia de payload real de hook en una corrida controlada; solo si
H1 se confirma se cambia el hook. Si no hay evidencia, el Change documenta H1 como UNCONFIRMED y no toca hooks.
**Boundaries.** Sin scheduler, worktree manager ni locks; ownership sigue siendo contractual salvo evidencia. **Dependencias.** 1 (misma
superficie `scope.py`/`repo.py`). **Aceptación.** (a) dos Changes abiertos con scopes disjuntos validan limpio cada uno; (b) un archivo en
ambos scopes o en ninguno produce hallazgo; (c) cadena inválida ajena → fail-closed; (d) 4A: evidencia real adjunta o decisión documentada de
no cambiar el hook; (e) ningún cambio de hook sin test con payload no sintético. **Riesgos.** Debilitar el scope → mitigado por (b)/(c).
**Diferido.** Ownership por instancia en hook.

### Change 5 — Upgrade & Migration Resilience
**Objetivo.** Nunca dejar silenciosamente un proyecto `half old / half new`.
**Scope.** (i) Test genérico de completitud del manifest (todo módulo runtime importable desde el árbol instalado está en `MANIFEST`; cierra la
clase de bug de v0.10); (ii) operación de upgrade explícita v0.10 → v0.11 con dry-run por defecto, que actualiza managed assets
no modificados y reporta drift sin adoptarlo; (iii) detección y recovery soportado de instalación/migración interrumpida (staging huérfano,
journal), en lugar de «revisar a mano»; (iv) Doctor post-upgrade con remedio accionable en `HARMESSI-VERSION`; (v) idempotencia; (vi)
preservación intacta de datos del proyecto: customizaciones de guardrails y amendments, `GLOSSARY.md`, ledger, approvals, Cards, Data Contracts.
**Boundaries.** Sin rollback entre versiones mayores ni downgrade; sin migrar datos del proyecto salvo que un schema de Changes 2/3 lo exija;
Doctor sigue corriendo desde el checkout salvo hallazgo contrario. **Dependencias.** 2 y 3 (si introducen schema nuevo), después de 1 y 4 para
que sus módulos entren al manifest. **Aceptación.** (a) un módulo no listado hace fallar un test; (b) upgrade sobre un proyecto v0.10
sintético termina en estado consistente y es idempotente; (c) interrupción simulada en cada fase → re-ejecución converge o aborta con
instrucción de recovery, nunca estado mixto silencioso; (d) los archivos project-owned quedan byte-idénticos; (e) Doctor verde post-upgrade.
**Riesgos.** El mayor de la versión: pérdida de datos del proyecto → siempre dry-run por defecto y backups del journal.
**Diferido.** Plataformas no Windows reales (CI).

### Change 6 — v0.11 Release Hardening + Dogfooding Evidence
Integración, sin features. Regresión completa única, fresh install, upgrade v0.10 → v0.11, recovery de migración parcial, Doctor, privacidad,
manifest, hashes managed, smoke de release, notas, versión `0.11.0`. **Dogfooding mínimo reproducible con fixtures sintéticos:** (A) proyecto nuevo
creado con v0.11; (B) proyecto representativo instalado como v0.10 y actualizado a v0.11. El uso corporativo real alimenta v0.12; no bloquea.
**Dependencias.** 5. **Aceptación.** Ambos escenarios documentados con comandos y salida; regresión verde; sin push/tag sin aprobación humana.
