## Composable Engineering & Data Science Skills

Registrado 2026-10-01 (feedback externo, preservado como línea de evolución -- NO implementado en
v0.8, NO contrato estable todavía, sujeto a revisión al congelar el alcance real de v0.10).

**Objetivo**: formalizar skills metodológicas pequeñas, combinables y contextuales, manteniendo
pocos roles/agentes estables -- Harmessi no crea un agente nuevo por cada capacidad, ni convierte un
único Lead en un mega-agente con toda la metodología embebida.

**Separación conceptual** (dirección arquitectónica, ver `ARCHITECTURE.md` §7 para su registro
formal):

- **Agent/Role** = quién trabaja y con qué permisos (Lead, writer, reviewer, metodólogo -- ya
  existentes, estables).
- **Skill** = cómo abordar metodológicamente una clase de problema (pequeña, componible,
  contextual -- selección del Lead según la tarea).
- **Runtime/Tool** = qué se ejecuta determinísticamente y deja evidencia (ya existente,
  `tools/leadrun/`).

```
Lead
  ↓ selecciona skills
domain-modeling / diagnosing-bugs / test-first / codebase-design / ...
  ↓
writer / reviewer / metodólogo
  ↓
runtime gobernado
  ↓
evidence / governance
```

**Candidatas iniciales** (nombres y alcance exacto quedan para SDD futuro, no se congelan acá):

1. **problem-framing / grill-me** -- clarificar qué se quiere construir; detectar requisitos
   ambiguos; separar objetivo, restricciones y criterios de aceptación.
2. **domain-modeling** -- lenguaje de dominio compartido: términos, definiciones, unidad de
   análisis, población, eventos, estados, relaciones, sinónimos, términos que parecen iguales pero
   NO lo son, invariantes conceptuales, ambigüedades que requieren decisión humana. Artefacto
   conceptual candidato: `GLOSSARY.md` (nombre NO congelado hasta su SDD futuro). Separación
   obligatoria entre tres cosas que nunca se mezclan: domain model/glossary (qué significa un
   concepto) ≠ decision ledger (por qué se tomó una decisión) ≠ Data Contract (qué
   estructura/evidencia esperamos de los datos). El domain model es propiedad del PROYECTO, nunca
   branding ni conocimiento hardcodeado del harness.
3. **test-first / TDD** -- NO aplicado dogmáticamente a todo Data Science. Diferenciar: software
   determinista → TDD/red-green-refactor; data contracts/pipelines → invariants/test-first; EDA →
   evidence/validation-first; modelado → protocolo de evaluación/scientific validity.
4. **diagnosing-bugs** -- proceso sistemático (reproduce → minimize → formulate hypothesis →
   instrument → fix → regression test), evitando prueba/error aleatorio.
5. **codebase-design** -- arquitectura, boundaries, ownership, coupling, impacto, consistency.
6. **code-review** -- revisión técnica: correctness, contracts, backward compatibility, security,
   maintainability.

**Relación de `domain-modeling` con autonomía** (motivación principal de la candidata #2):
comportamiento futuro deseado -- brief/objetivo → el Lead identifica vocabulario relevante →
consulta el domain model existente del proyecto → si el concepto ya está definido y aprobado,
reutiliza → si hay ambigüedad material de negocio, business checkpoint → el humano define → el
domain model queda actualizado/trazable → el Lead continúa. Evita volver a preguntar en cada Change
qué es un "cliente activo", qué significa "potencial", cuál es la unidad de análisis, qué evento
define una baja, qué población entra, qué fecha manda. Conocimiento INFERIDO por el LLM nunca se
convierte automáticamente en definición de negocio aprobada -- toda definición de dominio sigue el
mismo principio de aprobación humana que el resto de Harmessi.

**Antes de implementar cualquiera de estas skills**: auditar qué capacidades YA existen en el Lead,
reviewer, metodólogo, SDD, impact (`tools/dsimpact`), tests, remediation -- no duplicar una
capacidad solo porque tenga otro nombre. El objetivo es extraer/reutilizar metodología componible
ya presente, no inflar un catálogo.

**Principios de la arquitectura de skills** (dirección, NO contrato estable todavía):

```
Lead
  ↓
skill selection/composition
  ↓
small methodological skills
  ↓
stable roles
  ↓
governed runtime
  ↓
evidence
```

- una skill NO obtiene permisos adicionales por existir -- los permisos vienen del rol/runtime;
- una skill NO bypassa STOP;
- una skill NO instala dependencias;
- una skill NO cambia governance;
- la composición de skills debe ser observable/trazable cuando afecte un Change;
- skills específicas de un proyecto deberían poder existir sin modificar el core de Harmessi;
- evitar mega-skills;
- evitar un catálogo enorme antes de tener casos reales (no diseñar todavía un marketplace/plugin
  framework).

No agregar grandes familias funcionales nuevas salvo necesidad justificada (regla ya vigente de
este documento, arriba) -- esta sección es una línea de evolución a preservar, no una adición al
alcance actual de v0.10.

## Cross-platform managed-file hashing / line endings

Registrado 2026-10-01, deuda real encontrada durante el release de v0.8.0 (NO implementado todavía,
NO contrato estable, sujeto a revisión al congelar el alcance real de v0.10).

**Problema**: `tools/ds_init/control.py::sha256_de_archivo` hashea bytes crudos (modo `"rb"`, sin
normalización de fin de línea) para detectar drift de archivos administrados
(`tools/harmessi/doctor.py::HARMESSI-DRIFT`). En Windows, `core.autocrlf` puede reescribir LF↔CRLF
de un archivo administrado durante `checkout`/`merge`, cambiando sus bytes (y por lo tanto su
sha256) sin que el contenido lógico haya cambiado.

**Hallazgo real durante el release de v0.8.0**: `control.json` se había regenerado en `v0.8-dev`
antes del merge a `main`; el merge/checkout posterior normalizó a CRLF varios archivos nuevos de
v0.8 que se habían creado con LF, produciendo 19 falsos `HARMESSI-DRIFT` sobre archivos administrados
reales (nunca un `ERROR` -- `STATUS_NA`/`WARN` no cuentan como tal -- pero sucio para un release
recién publicado). Resuelto para v0.8.0 regenerando `control.regenerar_control(...)` directamente
sobre el árbol final ya mergeado de `main` (commit `8a8d6ec`), no sobre un estado intermedio de la
rama de desarrollo -- un workaround operativo, no una corrección estructural del mecanismo de hash.

**Evaluar en v0.10** (sin congelar todavía cuál, el SDD futuro decide):

- canonicalización de fin de línea antes de hashear (normalizar a LF antes de `sha256`, mismo
  criterio que `tools/dsguard/core.py::hash_lf_v1` ya usa para la aprobación de artefactos SDD);
- política explícita de newline normalization declarada en el manifiesto/`.gitattributes`;
- content hashing lógico (AST/semántico) en vez de hashing de bytes crudos, si el costo lo justifica;
- o un mecanismo portable equivalente que dé el mismo resultado en Windows/Linux/Mac sin depender de
  la configuración local de `git`.

**Objetivo**: que `HARMESSI-DRIFT` detecte modificación LÓGICA de un archivo administrado, nunca una
diferencia accidental de fin de línea entre plataformas o entre el momento de regenerar
`control.json` y el checkout final.

Este archivo se reemplaza por un desglose completo de Changes cuando se congele el alcance real de
v0.10, al cerrar v0.9.

## Approval origin / human authorization authenticity

Registrado 2026-10-02 (hallazgo del audit de `20261002-exec-approval-registration`). Deuda explícita de
security-hardening; NO es requisito de v0.9 y NO se diseña todavía.

Problema: un proceso que pueda ejecutar el CLI podría invocar una operación de aprobación
(`ds_guard approve`, `ds_guard exec approve`) declarando un `--usuario`, porque el harness confía hoy en
el acto de registro y no dispone de una primitive técnica que pruebe human-origin. Las aprobaciones
actuales son *recorded human declarations under the harness trust model*: no son firma criptográfica,
prueba de identidad, prueba de que la persona tipeó el comando ni non-repudiation. Un `ApprovalRef` es
una referencia verificable a una aprobación registrada por Harmessi, no prueba criptográfica de autoría.

Evaluar en v0.10, sin diseñarlo ahora: confirmación humana interactiva; señal de presencia de
usuario/terminal confiable; canal de aprobación separado; aprobaciones firmadas; mecanismo atado a
usuario/OS; u otra primitive compatible con los distintos providers.

Objetivo: poder distinguir, cuando haga falta, `recorded approval` de `technically human-originated
approval` sin romper portabilidad ni provider neutrality.

## Authorized-scope mutation UX

Registrado 2026-10-02 (observado durante Change 0 de v0.9). Deuda de UX/autonomía; NO se implementa en v0.9.

Problema: `ds_guard` no tiene hoy una interfaz soportada para ampliar o modificar
`alcance.rutas_autorizadas` de un Change; durante Change 0 y el corrective `exec-approval-registration`
fue necesario editar `control.json` (archivo interno) a mano para autorizar tests y rutas nuevas.
Además `ds_guard validate` evalúa `ALCANCE-RUTA` sobre todo el working tree y el historial desde el
baseline, sin distinguir Changes abiertos en paralelo; se resolvió re-baselineando.

Dirección futura: una operación first-class y auditada para modificar el scope autorizado (con registro
de quién/cuándo/por qué y límites claros), sin edición manual del archivo interno, y un validator
consciente de múltiples Changes abiertos.
