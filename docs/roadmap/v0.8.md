## Origen: feedback de reutilización real

Al instalar Harmessi en un proyecto externo aparecieron dos limitaciones de producto. Ambas están
confirmadas contra el código actual (no son impresiones):

**Limitación 1 — la autonomía no llega al harness instalado.** Harmessi tiene un contrato de
autonomía fuerte para desarrollarse a sí mismo (`README.md` de este directorio), pero el harness que
se instala en un proyecto modela `agente escribe → humano ejecuta → humano devuelve output → Lead
continúa`:

- `agent_python_data_engineer.md.tmpl`: el writer "no ejecuta código ni notebooks" (correcto, y se
  mantiene);
- `SKILL_lead_data_scientist.md.tmpl`, «Gestión de sesiones → Pausa»: una de las causas de pausa es
  "hace falta ejecutar algo que ningún agente puede correr en esta versión"; «Restricción de esta
  versión» repite el límite;
- `sdd.md.tmpl` §6 (pasos "El usuario ejecuta y trae el output al chat") y §7 (`en_verificacion` =
  "esperando que el usuario ejecute"; `pausada_bloqueada` incluye "ejecución que ningún agente puede
  correr");
- un proyecto que quiere operar de forma autónoma hoy tiene que editar a mano archivos
  administrados; `harmessi doctor` lo reporta como `HARMESSI-DRIFT` (`WARN`, ver
  `_check_hashes_drift`) y una sincronización posterior puede pisar o chocar con esa edición.

**Limitación 2 — el core asume archivos.** Harmessi debe ser agnóstico de infraestructura, pero su
único observador de datos está atado a archivos:

- `ds_profile.io_readers.abrir_lector(ruta)` solo entiende CSV/Parquet; `generar_perfil(ruta_input:
  Path)` recibe una ruta; `profile.json` persiste `dataset_path`;
- `tools/datacontracts/validation.py` evalúa contratos sobre la forma exacta de `profile.json`
  (`schema`, `columnas_detalle`, `sampling.activo`, `filas`) y sobre el vocabulario de tipos de
  `ds_profile`;
- el guard de holdouts (`pathguard`, `guardrails.json`) es por ruta: una tabla sellada de una base
  de datos no tiene ruta que proteger.

No hay ninguna abstracción entre "dónde está el dato" y "qué observó Harmessi".

## Objetivo

> Harmessi es **opinionated sobre governance** y **agnóstico sobre infraestructura y dominio**.

Define contratos, responsabilidades, evidencia, gates, seguridad y trazabilidad. **No** define dónde
vive el dato, qué base usar, qué driver, qué librería SQL, qué modelo entrenar ni qué algoritmo
elegir: eso lo personaliza el proyecto mediante interfaces soportadas, sin editar archivos
administrados.

v0.8 resuelve dos pilares con **un solo runtime**:

1. **Autonomía real del proyecto instalado** (modos `autonomous` / `supervised` como política sobre
   el mismo runtime, no dos arquitecturas).
2. **Abstracción de fuente extensible** (`fuente real → extensión del proyecto (adapter) →
   observación neutral → Harmessi: contratos/governance/evidence/reporting`).

Reparto congelado de responsabilidades:

- **Harmessi define:** contratos, governance, evidencia, ejecución gobernada, seguridad,
  trazabilidad y gates.
- **El proyecto define:** dónde viven los datos, cómo conectarse, driver, librerías, queries, APIs,
  credenciales y la implementación concreta del adapter.
- **El core no ramifica** por CSV, Parquet, SQL, PostgreSQL, SQL Server, warehouse, API ni proveedor
  cloud; ninguna de esas tecnologías es dependencia del core.

Principio operativo (heredado, permanente):

> LLM decide lo semántico; el binario calcula y hace cumplir lo determinista.

## Métrica funcional clave (gate de producto)

```
Given:  un proyecto nuevo,
        una fuente de datos válida,
        un objetivo de análisis cerrado (propuesta aprobada por el humano),
        modo autonomous,
When:   se inicia el Lead,
Then:   Harmessi completa
        inspección → planificación → escritura → ejecución → corrección
        → tests → evidencia → reporting
        sin pedirle al humano que ejecute código ni que copie outputs,
        salvo que ocurra un STOP material.
```

Esta es una capability fundamental de producto. Se mide sobre **artefactos**, no sobre impresiones:

- el ledger de ejecución (Change 2) registra `executed_by` en cada corrida: el resultado exige
  **0 corridas con `executed_by: human`** y 0 outputs pegados por el humano;
- las intervenciones humanas del run se clasifican con los artefactos existentes (aprobación de
  propuesta, decision ledger, notas de sesión): solo son válidas la aprobación inicial del objetivo
  y los STOP materiales;
- el escenario se corre con un **humano proxy que no puede ejecutar nada**: si el Lead le pide
  ejecutar código o pegar un output, el run se detiene y el gate falla.

Limitación declarada: el Lead es un LLM, así que este gate es una corrida end-to-end registrada
(evidencia en `verification.md` del hardening), no un test unitario determinista. Lo determinista
(política, runtime de ejecución, adapters, ledger) sí tiene tests unitarios y de contrato.

## Arquitectura — pilar 2: fuentes

```
SOURCE                      cómo/dónde están los datos
   ↓                        (archivo, PostgreSQL, API, object storage, propietario, varias...)
ADAPTER (extensión del proyecto)
   ↓                        cómo el proyecto obtiene evidencia de esa fuente
                            (código y dependencias del proyecto, fuera del core)
SOURCE OBSERVATION          representación neutral, determinista y serializable de lo observado
   ↓
HARMESSI                    contratos, validación, governance, evidence, reporting
```

El core de Harmessi trabaja **solo** sobre `SourceObservation`. No ve SQL, paths ni DataFrames.

### Conceptos candidatos (los nombres exactos se deciden en SDD; no congelados)

- **`DataSourceRef`** — referencia lógica (`customers`, `transactions`, `model_features`,
  `external_scores`), no un archivo. Declara: `source_id`, rol, referencia al adapter, `access_mode`
  (`read` por defecto), capacidades, referencia opaca a configuración, metadata de
  sensibilidad/governance y extensiones `x_`. **Nunca** contiene passwords, connection strings con
  secretos, tokens ni credenciales: solo referencias (p. ej. el *nombre* de una variable de entorno).
- **`DataSourceAdapter`** — extension point del proyecto; sabe hablar con la fuente. Contrato
  mínimo: declarar capacidades y producir una observación a partir de un pedido acotado (qué facetas,
  con qué corte temporal, con qué exactitud). El pedido **no contiene texto de consulta**: cómo se
  obtiene la evidencia (SQL, request HTTP, lectura de Parquet) es interno del adapter.
- **`SourceCapabilities`** — lo que el adapter declara poder hacer. Harmessi solo pide lo declarado.
- **`SourceObservation`** — contrato neutral y determinista (ver abajo).
- **`SourceProvenance`** — de dónde y cómo salió la observación (ver abajo).

### `SourceObservation`

Contiene, cuando existe evidencia: `source_id`, schema observado, observaciones de campo/tipo (con
familias de tipo **neutrales**, las mismas de `ContractField` de v0.7, no el vocabulario de
`ds_profile`), conteo de filas, nulos, min/max, evidencia de unicidad, evidencia de dominio, límites
temporales, snapshot/cutoff, hashes/fingerprints, metadata de muestreo y **exactitud por dato**
(`exact` / `approximate`). Serialización con orden determinista, versión de schema explícita y hash
de contenido que excluye `generated_at`.

Reglas:

- **Ausencia de evidencia no es `null` ni `0` ni `PASS`**: la observación distingue "no observado"
  de "observado y vacío". Una regla de contrato sin faceta observada queda `WARN` (aplicable pero no
  verificable) o `N/A` (no aplica), **nunca** `PASS` (extiende la decisión 3 de v0.7).
- El core **nunca ramifica** sobre el tipo de fuente. `source_kind` existe solo como etiqueta
  informativa de provenance; un test de neutralidad lo verifica.
- Ningún tipo del core contiene rutas, hosts, DSN ni texto de consulta. Un archivo local se
  referencia por su configuración en el registro del proyecto (repo-relativa), nunca dentro de la
  observación (lección de v0.7: `ds_profile` persiste `dataset_path` posiblemente absoluto).
- Las facetas que transportan **valores** (`min_max`, `domain`, top values) están sujetas a la
  sensibilidad declarada en `DataSourceRef`: una fuente `sensitive` puede exigir omitirlas o
  redactarlas en la evidencia persistida (la observación registra que fueron omitidas, no las omite
  en silencio).

### `SourceCapabilities`: dos ejes, no una lista plana

La lista candidata del feedback mezcla dos cosas distintas; el análisis propone separarlas:

1. **Facetas de observación** que el adapter puede producir, cada una con la exactitud que
   soporta: `schema`, `row_count`, `null_counts`, `min_max`, `uniqueness`, `domain`, `time_bounds`,
   `snapshot`, `fingerprint`. Es lo único que el core de Harmessi puede **pedir**.
2. **Operaciones** que el adapter expone al código del proyecto: `sample`, `read`, `write`. El core
   no las invoca en v0.8; existen para que el proyecto (y su governance) las declare.

Decisión de análisis: **`execute_query` no entra al vocabulario del core**. Pedirle a un adapter que
ejecute una consulta reintroduciría SQL en el core. Un adapter SQL usa consultas internamente para
producir facetas; Harmessi nunca lo sabe.

`read` es el default seguro (`access_mode: read`). `write` exige capacidad declarada **y** policy
explícita de origen humano (ver M2); en v0.8 `write` es vocabulario reservado con política
deny-by-default y un test de que ningún camino de código de Harmessi escribe a una fuente. Los
límites reales de este control están en "Límites honestos".

### `SourceProvenance`

`source_id`, identificación y versión del adapter, hash del código del adapter (para detectar que
cambió entre observaciones), momento de observación (`generated_at`, declarado aparte del hash de
contenido), snapshot/cutoff/as-of, `access_mode` efectivo, `source_kind` informativo, versiones de
herramientas. Sin rutas absolutas, sin hosts, sin credenciales.

### Relación con `ds_profile` y Data Contracts v0.7 (backward compatibility)

```
archivo local ─► ds_profile (SIN CAMBIOS) ─► profile.json v1 ─► bridge ─► SourceObservation
otra fuente   ─► adapter del proyecto ────────────────────────────────► SourceObservation
                                                                              │
                                              DataContract validation ◄───────┘
```

- `ds_profile`, su CLI y `profile.json` **schema_version 1 no cambian**. El bridge es aditivo:
  un conversor `profile.json → SourceObservation` (función pura sobre el `dict` ya cargado, respetando
  el guard de holdout al leer) y un adapter de archivo mínimo que orquesta `ds_profile` + conversor.
  El mapeo de tipos `ds_profile` → familias neutrales (hoy embebido en `validation.py`) pasa a vivir
  en el bridge.
- `validate_contract(contract, profile)` y `validate_contract_against_profile_file(...)` **conservan
  firma, códigos `CONTRACT-*` y resultados**. La validación pasa a tener un evaluador nativo sobre
  `SourceObservation`; las funciones v0.7 son wrappers (`profile → observación → evaluador`).
  Criterio no negociable: **paridad exacta** de resultados sobre todos los fixtures de v0.7. Es el
  punto que toca un contrato público de v0.7 → **decisión material M1 (confirmada)**: un único
  evaluador, sin segundo motor de validación; el evaluador nativo no lee archivos; el wrapper
  conserva las verificaciones de acceso/holdout que corresponden.
- La evidencia de fuente no-archivo entra a reporting y a `qualityevidence` **como archivo con hash**
  (el `observation.json` persistido), por el mismo camino ya existente: sin cambio de schema de
  manifest y sin que los paquetes se importen entre sí.
- Extender `ds_profile` para leer SQL/APIs queda **prohibido**: sería convertir un observador de
  archivos en un catálogo de conectores.

### Mecanismo de extensión (decisión material M6, confirmada: E1)

Evaluado contra la arquitectura actual (paquetes solo-stdlib, manifiesto de archivos administrados
con hashes, archivos de proyecto en `.harmessi/`):

| Opción | Descripción | Estado en v0.8 |
|---|---|---|
| **E1** | Registro del proyecto + `módulo:callable` resuelto por `importlib` desde código del proyecto, en el `.venv` del proyecto, ejecución en proceso | **Elegida.** Declarativo y auditable; un archivo de proyecto, sin tocar administrados; las dependencias (psycopg, SQLAlchemy, driver corporativo) son del proyecto |
| E2 | `entry_points` de paquetes instalados (`importlib.metadata`) | **Fuera de v0.8; no se implementa.** Descubrimiento implícito y difícil de auditar; exige empaquetar el adapter |
| E3 | Comando externo que emite `SourceObservation` JSON por stdout | **Fuera de v0.8.** Queda conceptualmente compatible: como el formato de cable ya es la observación JSON, agregarlo en el futuro no cambia el core |

Forma conceptual (registro versionado en git, propiedad del proyecto, sin secretos):

```
source:  customers
adapter: my_project.sources.sql_customers:CustomerSource
access:  read
sensitivity: internal
config_ref: env:CUSTOMERS_DSN        # nombre de la variable, nunca su valor
```

- El registro vive en un archivo **del proyecto** (ubicación exacta en SDD, p. ej. bajo
  `.harmessi/`), **no** está en el manifiesto de instalación ni en `control.json["archivos"]`. Por
  construcción no puede producir `HARMESSI-DRIFT`: el drift solo se calcula sobre archivos listados
  ahí. Una customización válida no puede generar drift por usar el extension point soportado.
- El adapter vive en el código del proyecto y corre en el `.venv` del proyecto, en proceso. Lo
  escribe el writer y lo revisa el reviewer, como cualquier código; su hash forma parte de
  `SourceProvenance`.
- Las dependencias específicas las instala el proyecto. Un error o fallo de import del adapter se
  reporta como `technical_error` que pide acción humana; **Harmessi nunca instala drivers ni
  dependencias del adapter**. Una dependencia nueva *dentro* de Harmessi es STOP material.
- No hay catálogo de conectores ni dependencias específicas de fuentes (PostgreSQL, SQL Server,
  Snowflake, BigQuery, pandas, SQLAlchemy, etc.) en el core de Harmessi.
- `harmessi doctor` valida el registro de forma **estática** (schema, adapter resoluble como archivo,
  scan de secretos) y **no** importa ni ejecuta código del proyecto.

### Seguridad y secretos

- `DataSourceRef` solo admite referencias (`env:NOMBRE`, nombre de secreto). Un scan determinista
  rechaza claves tipo `password`/`token`/`secret`/`api_key`, URLs con credenciales embebidas
  (`esquema://usuario:clave@host`) y valores con forma de credencial. Corre sobre el registro
  (Doctor y CLI), antes de persistir una observación y sobre la evidencia. Es **por patrón, best-effort
  y así se declara**; la garantía fuerte sigue siendo que `pathguard` deniega `.env`/claves y que el
  adapter, no Harmessi, maneja las credenciales.
- Las observaciones y la evidencia son portables: sin rutas absolutas, sin DSN, sin hosts.
- Una fuente **sellada** (holdout) se declara por `source_id` en la policy **de origen humano**
  (M2), no en el registro que puede editar el writer. La policy humana establece el **máximo**
  permiso posible; el registro del proyecto puede únicamente **restringirlo**: permiso efectivo =
  policy humana ∩ registro del proyecto. El registro nunca amplía permisos.
- El runtime de observación consulta la policy **antes** de observar: una fuente sellada no puede
  observarse aunque el registro del proyecto la declare. Para fuentes file-backed se mantiene la
  coherencia `source_id` ↔ ruta/holdout (una fuente en archivo cuya ruta cae en un holdout no puede
  quedar sin sellar por `source_id`, ni al revés).

### Límites honestos (a documentar, no a ocultar)

- Harmessi garantiza el acceso **que media** (observar vía adapter declarado, capacidades, sealed
  por `source_id`, evidencia sin secretos). **No** puede sandboxear código del proyecto: un script que
  abre una conexión por su cuenta no pasa por Harmessi. Es el mismo límite ya documentado para
  `Bash`/`PowerShell` (best-effort) y para `reporting` (`ARCHITECTURE.md` §5).
- Los writes a archivos del repo se detectan (manifest + fsdiff + cuarentena); los writes a una base
  o API desde un script **no** son detectables por Harmessi. Para fuentes no-archivo, `read-only` se
  sostiene por: `access_mode` declarado, revisión del código por el reviewer, cuenta de solo lectura
  en el adapter (responsabilidad del proyecto) y STOP ante cualquier write autorizado.
- Un adapter en proceso comparte permisos con el proceso que lo carga.

## Arquitectura — pilar 1: autonomía

### Ciclo objetivo

```
humano: objetivo y decisiones materiales (aprobación de propuesta)
        ↓
Lead gobierna y ejecuta
        ↓
writer escribe (python-data-engineer; NO ejecuta)
        ↓
reviewer revisa código antes de ejecutar (read-only)
        ↓
Lead ejecuta scripts/tests/notebooks vía runtime gobernado
        ↓
Lead analiza outputs; remedia dentro del presupuesto (writer corrige) y re-ejecuta
        ↓
metodólogo (read-only) cuando hay interpretación metodológica
        ↓
Lead verifica y cierra; el binario escribe la evidencia
        ↓
humano interviene SOLO ante STOP material
```

Se mantiene: un solo writer, reviewers read-only, remediation acotada, separación de
responsabilidades, STOP materiales y trazabilidad. **El writer no recibe ninguna capacidad de
ejecución** (su lista de `tools` en el frontmatter no cambia; un test lo fija).

### Un runtime, dos políticas

`autonomous` y `supervised` **no son dos arquitecturas**: son dos columnas de la misma tabla de
política. Cada acción del runtime pertenece a una **clase de acción**; la política resuelve, de forma
determinista y como dato (no como prosa duplicada en dos skills), **quién ejecuta** y **qué
aprobación requiere**.

| Clase de acción | `autonomous` | `supervised` |
|---|---|---|
| Diagnóstico de solo lectura (`ds_guard status/validate`, `git status/diff`, `ds_profile`, observar una fuente autorizada y no sellada) | Lead | Lead |
| Ejecutar código del proyecto (script, test, notebook vía runner) dentro del alcance aprobado | Lead, por el runtime gobernado; sin aprobación por corrida | el humano ejecuta, o aprueba explícitamente cada corrida y el Lead ejecuta (queda `executed_by`) |
| Aprobación del hash/manifest de una corrida | política: referencia a la aprobación humana de la propuesta + reviewer sin hallazgos abiertos | humano |
| Aprobar propuesta / objetivo / decisiones materiales (incluida la pre-aprobación de decisiones metodológicas listadas, ver M3) | humano | humano |
| Continuar una decisión metodológica **listada y aprobada** en la propuesta | Lead, por política (referencia a la aprobación humana) | Lead propone; humano aprueba |
| Decisión metodológica **no listada** | **STOP humano** | **STOP humano** |
| Transiciones SDD posteriores a la aprobación de la propuesta | Lead | Lead propone; el humano aprueba las marcadas |
| Reinvocación correctiva dentro de una ventana vigente | Lead | Lead |
| `remediation extend` (ampliar la ventana) | **STOP humano** | humano |
| Abrir/cerrar sesión | Lead, dentro de topes agregados | como hoy (confirmación al abrir) |
| Holdout/sellado, secretos, instalar dependencias, escribir a una fuente o a `data/raw` | **STOP** | **STOP** |
| Commit / tag / publicación | humano en ambos modos | humano |

La tabla es el contrato; el skill del Lead instalado la consulta y no la duplica. Lo que el binario
puede hacer cumplir se hace cumplir en el binario (p. ej. el runtime de ejecución rechaza una corrida
en `supervised` sin aprobación humana registrada); lo semántico sigue siendo del Lead.

### Contrato de autonomía del proyecto instalado

Distinto del contrato de `README.md` (que gobierna cómo se desarrolla Harmessi). Para cada Change
aprobado del proyecto: `explorar → SDD → escribir → revisar → ejecutar → analizar → remediar →
re-ejecutar → verificar → cerrar`, sin pedir confirmación humana entre pasos normales.

**STOP material** (el humano decide; en ambos modos):

1. acceso a holdout/dato sellado (por ruta **o** por `source_id`);
2. decisión metodológica o de negocio fuera de lo aprobado (target, features, universo, split,
   métrica, umbral, qué se descarta);
3. duda de leakage sin resolver (regla ya existente de `CLAUDE.md`);
4. dependencia nueva a instalar (incluido un driver de base de datos);
5. escribir fuera del alcance declarado, escribir a una fuente, o a `data/raw`;
6. un secreto/credencial que solo el humano puede proveer, o secreto expuesto;
7. riesgo de pérdida o corrupción de datos o artefactos no regenerables;
8. bounded remediation agotada;
9. reviewer o metodólogo demuestran que el enfoque aprobado es incorrecto;
10. contradicción real entre requisitos o entre requisito y evidencia;
11. expansión sustancial de scope o cambio incompatible;
12. necesidad de bypass/excepción no prevista (guardrails, pathguard).

**LÍMITE (no es STOP):** el presupuesto de sesión (tiempo, tareas, subagentes, reintentos) y los
topes agregados. Agotarlo produce un **checkpoint de cierre o pausa resumible**, sin pregunta al
humano. **El presupuesto limita la autonomía; no es una puerta de aprobación**: dentro del
presupuesto el Lead no pide permiso para continuar, y agotarlo no exige una decisión, solo una
nueva sesión. Por eso abrir/cerrar sesiones exige topes **agregados** (sesiones y tiempo totales
del objetivo); sin ellos, encadenar sesiones evadiría el límite.

**Errores técnicos** (fuente no disponible, test que falla, timeout) no son STOP ni resultado de
calidad: se reportan como `technical_error`, el Lead puede remediar dentro de la ventana y, agotada,
aplica el STOP 8.

### Reglas de la autonomía

- **La autonomía es una concesión humana.** El modo, los límites agregados, las fuentes selladas, los
  permisos de lectura/escritura de fuentes y cualquier concesión sensible viven en la policy de
  origen humano (M2), fuera del alcance de escritura de cualquier agente. Esa policy es el
  **máximo** permiso posible; el registro del proyecto solo puede restringirlo (efectivo = policy ∩
  registro). Un agente puede **estrechar** (pasar de `autonomous` a `supervised` en una sesión),
  nunca ampliar.
- **La policy es fail-closed frente a versiones que no la entienden (M2).** La policy lleva una
  versión/schema reconocible. Un componente instalado (runtime o guard) que no entienda una
  capacidad de seguridad que la policy requiere **no puede** habilitar `autonomous` ni gobernar
  `sealed_sources` en silencio: deniega o degrada a `supervised`, nunca ignora. `harmessi doctor`
  detecta esa incompatibilidad (ERROR cuando una policy exige una capacidad que la versión instalada
  no soporta). El upgrade del runtime y del guard es **previo** a permitir `autonomous`, no
  posterior. Hoy `pathguard.cargar_config` ignora las claves desconocidas y no valida `version`; por
  eso este requisito es explícito y no un supuesto.
- **Las aprobaciones por política son distinguibles y trazables.** Toda aprobación hecha por la
  política deja `approved_by: policy:autonomous` más la referencia (hash) a la aprobación humana de
  la propuesta que la habilita. Nunca se registra como si la hubiera dado el humano.
- **Decisiones metodológicas pre-aprobadas (M3).** Una propuesta aprobada puede contener decisiones
  metodológicas pre-aprobadas solo si están enumeradas, estructuradas, dentro del alcance del
  Change, aprobadas por el humano y vinculadas al hash de esa propuesta. Listada y aprobada →
  continúa por política; no listada → STOP humano. La unidad de aprobación es la propuesta SDD
  aprobada por Change (con hash), `control.json` y el decision ledger; **no** se crea una "carta"
  multi-Change salvo que el audit del Change 0 demuestre objetivamente que la propuesta existente
  es insuficiente. El formato parseable de esa sección queda para SDD.
- **El binario escribe la evidencia de ejecución; el Lead no edita archivos.** Consistente con la
  regla vigente: el Lead no escribe, el writer escribe el código, el runtime registra.
- **El vocabulario de estados y los schemas de SDD/control son solo aditivos**: los artefactos de un
  proyecto v0.7 siguen siendo válidos. `en_verificacion` pasa a significar "ejecución y verificación
  en curso" (el Lead ya no espera al usuario) sin agregar estados.
- **Los fallos de ejecución consumen la remediation acotada existente** (`retry_tecnico`/`bug`, mismos
  contadores y ventanas): no se crea un segundo contador.
- El writer recibe los logs de ejecución como archivos legibles de la corrida (el Lead los cita en el
  campo 2 de la delegación), no pegados por el humano.

### Runtime de ejecución del Lead

Objetivo: que el Lead ejecute lo necesario **sin convertirse en un shell irrestricto**. La
**decisión material M5 (confirmada)** fija cómo se hace cumplir en v0.8: runtime gobernado +
evidencia + auditoría + guardrails existentes. El hook estricto global de allowlist queda diferido a
`v0.10.md` y deberá reutilizar la misma función pura de evaluación, sin crear otra allowlist.

**Condición congelada (M5): solo las ejecuciones realizadas mediante el runtime gobernado de
Harmessi cuentan como evidencia válida de ejecución y de cierre de un Change autónomo.** Una
ejecución directa (p. ej. `python script.py` lanzada por Bash fuera del runtime) puede ocurrir
técnicamente, porque Harmessi no es un sandbox, pero:

- no satisface el gate de ejecución;
- no genera evidencia válida de cierre;
- no puede usarse para afirmar que el Change fue verificado;
- debe aparecer como hueco o inconsistencia si era necesaria para producir el resultado.

En modo `autonomous`, el contrato del Lead indica que scripts, tests y notebooks gobernables se
ejecutan mediante el runtime correspondiente. La garantía de v0.8 es **gobernanza + evidencia +
enforcement en las superficies controladas**; **no** es un sandbox total del proceso y no se afirma
que v0.8 prevenga toda ejecución directa.

- Formas de comando admitidas (allowlist declarativa, no regex permisivo): intérprete del `.venv`
  + script del proyecto dentro del alcance; intérprete + `-m pytest` sobre rutas del alcance; runner
  de notebooks con manifest; CLIs propias de Harmessi (`ds_guard`, `ds_profile`, `harmessi`).
  Cualquier otra forma: rechazada o STOP según la clase.
- Cada corrida lleva un **manifest** con hash del código, entradas/salidas permitidas, rutas
  prohibidas, timeout y criterio de éxito, y deja un **registro de ejecución** (comando, hash del
  código, exit code, duración, hash de salidas, resumen de stdout/stderr, `executed_by`, modo,
  referencia de aprobación). Reutiliza fsdiff, cuarentena y validaciones de `nbrunner`; no las
  reimplementa.
- Se respetan `pathguard`, secretos, `data/raw`, holdouts/`sealed`, `write_scopes` y las policies
  existentes. Límite honesto: dentro de un proceso ya autorizado un script puede abrir cualquier ruta;
  ese riesgo residual se mitiga con revisión previa, manifest, fsdiff/cuarentena y hash, y se declara.

## Decisiones de diseño del roadmap

Fijadas acá para que los SDD no las reabran; cambiarlas es cambio arquitectónico material (STOP).

1. **El writer no ejecuta.** `python-data-engineer` mantiene su conjunto de herramientas. La
   autonomía la ejerce el Lead.
2. **Un runtime, dos políticas.** `autonomous`/`supervised` se resuelven por una tabla de política
   de datos. No hay skills, agentes ni flujos paralelos por modo.
3. **El Lead ejecuta solo por el runtime gobernado.** Sin shell irrestricto; sin instalación
   automática de dependencias.
4. **El core opera sobre `SourceObservation`.** Sin paths, SQL ni DataFrames en los tipos del core;
   el core no ramifica sobre el tipo de fuente.
5. **Ausencia de capacidad o evidencia no es `PASS`.**
6. **Adapters, dependencias y credenciales son del proyecto.** Harmessi no los instala, no los
   persiste y no incluye un catálogo de conectores.
7. **`ds_profile` y `profile.json` v1 son estables**; el bridge es aditivo y la validación de
   contratos v0.7 conserva firma, códigos y resultados.
8. **Quality no es gate** (decisión 5 de v0.7, vigente): nada de esto modifica readiness ni promote.
9. **El presupuesto es un límite, no una aprobación** (LÍMITE vs STOP).
10. **La autonomía es una concesión de origen humano**; agentes solo pueden estrechar.
11. **Las aprobaciones por política son trazables y distinguibles** de las humanas.
12. **Sin dependencias nuevas en Harmessi**: stdlib. `sqlite3` de la stdlib solo aparece en el
    fixture del Case B del hardening.
13. **Schemas y vocabularios aditivos**: un proyecto v0.7 sigue siendo válido.
14. **Ninguna customización soportada requiere editar archivos administrados**; las superficies de
    extensión del proyecto quedan fuera del cálculo de drift por construcción.
15. **Las decisiones materiales M1-M6 tienen el mismo rango** (ver "Decisiones materiales
    confirmadas"): un único motor de validación de contratos; policy humana como máximo y registro
    que solo restringe, fail-closed; aprobación humana trazable por propuesta; `supervised` por
    defecto; solo el runtime gobernado produce evidencia válida de ejecución; extensión por
    `módulo:callable` en proceso.

## Reglas de arquitectura para el código de v0.8

Coherentes con `ARCHITECTURE.md` (nombres de paquetes y módulos se definen en SDD):

- el paquete de fuentes tiene un **core solo-stdlib** (tipos de referencia, capacidades,

## Decisiones materiales confirmadas (M1-M6)

Confirmadas explícitamente por el autor. Son materiales porque cada una toca un contrato público,
un límite de seguridad o la cantidad de intervención humana. Cambiarlas es cambio arquitectónico
material (STOP). Los nombres concretos de claves, firmas y formatos quedan para SDD.

### M1 — Evaluador de contratos sobre `SourceObservation`

Un único evaluador nativo sobre `SourceObservation`; las APIs públicas de v0.7 son wrappers:
`profile.json → bridge → SourceObservation → evaluador único`.

Congelado:

- `validate_contract` y las APIs públicas de v0.7 mantienen firma y comportamiento;
- códigos `CONTRACT-*` sin cambios;
- resultados idénticos sobre todos los fixtures de v0.7; el gate de paridad exacta es obligatorio;
- el vocabulario y los tipos propios de `ds_profile` quedan encapsulados en el bridge;
- el evaluador nativo **no lee archivos**;
- el wrapper existente conserva las verificaciones de acceso/holdout que correspondan;
- **no se crean dos motores de validación.**

SDD: firma interna del evaluador y representación exacta de la evidencia faltante.

### M2 — Policy humana de autonomía y fuentes

El archivo de guardrails del proyecto (`.claude/guardrails.json`), extendido de forma aditiva, es la
única policy humana protegida.

> La policy humana establece el **máximo** permiso posible. El registro del proyecto puede
> únicamente **restringirlo**. Permiso efectivo = policy humana ∩ registro del proyecto. El registro
> nunca amplía permisos.

Congelado como decisiones humanas protegidas: modo de autonomía; límites agregados;
`sealed_sources`; permisos de lectura/escritura de fuentes; cualquier concesión sensible de
autonomía.

**Cómo se gobiernan las fuentes sin filesystem** (SQL, API, warehouse; `pathguard` protege rutas y no
las ve): una fuente sellada se identifica por `source_id`; el runtime de observación consulta la
policy **antes** de observar; una fuente sellada no puede observarse aunque el registro la declare;
para fuentes file-backed se mantiene la coherencia `source_id` ↔ ruta/holdout.

**Fail-closed (requisito explícito):** un runtime o `pathguard` viejo que no entienda las claves
nuevas **no puede** habilitar `autonomous` ni gobernar `sealed_sources` en silencio. Se exige:

- versión/schema reconocible de la policy;
- Doctor capaz de detectar la incompatibilidad;
- comportamiento fail-closed cuando una capacidad de seguridad requerida no es entendida por la
  versión instalada;
- upgrade coherente del runtime/guard **antes** de permitir `autonomous`.

**Límite mantenido:** Harmessi no puede impedir que código arbitrario del proyecto abra directamente
una conexión fuera de sus interfaces gobernadas. Esto no se presenta como sandbox.

SDD: nombres concretos de claves, esquema de versión y mecanismo de degradación.

### M3 — Unidad de aprobación humana

Se reutiliza la propuesta SDD aprobada por Change, con hash, `control.json` y decision ledger. No se
crea una "carta" multi-Change salvo que el audit del Change 0 demuestre objetivamente que la
propuesta existente es insuficiente.

Una propuesta puede contener decisiones metodológicas pre-aprobadas **solo** si están enumeradas,
estructuradas, dentro del alcance del Change, aprobadas por el humano y vinculadas al hash de esa
propuesta.

- decisión metodológica listada y aprobada → puede continuar por política;
- decisión metodológica no listada → STOP humano;
- toda aprobación por política referencia la aprobación humana que la habilitó.

SDD: formato parseable concreto de la sección de decisiones pre-aprobadas.

### M4 — Default de autonomía

`supervised` es el default en instalaciones nuevas y en upgrades desde v0.7. `autonomous` siempre
requiere una concesión humana explícita.

Congelado: ningún upgrade activa `autonomous`; un proyecto v0.7 conserva su comportamiento; si el
instalador no recibe una elección explícita queda `supervised`; cambiar luego a `autonomous` requiere
modificar la policy humana por un mecanismo permitido. La métrica funcional de v0.8 se prueba con
`autonomous` habilitado de forma explícita.

SDD: mecanismo exacto (flag del instalador, comando o edición humana).

### M5 — Enforcement de ejecución del Lead

Para v0.8: runtime gobernado + evidencia + auditoría + guardrails existentes (`pathguard`, secretos,
`data/raw`, holdouts, hooks de presupuesto, timeout, hashes, fsdiff, cuarentena, ledger,
`executed_by`). El hook estricto global de allowlist queda diferido a `v0.10.md` y debe reutilizar la
misma función pura de evaluación, no crear otra allowlist.

Condición fundamental congelada: **solo las ejecuciones realizadas mediante el runtime gobernado de
Harmessi cuentan como evidencia válida de ejecución y de cierre de un Change autónomo** (detalle en
"Runtime de ejecución del Lead"). No se otorgan herramientas de ejecución al writer, no se crea un
shell irrestricto como interfaz de autonomía y no se afirma que v0.8 prevenga toda ejecución directa:
la garantía es gobernanza + evidencia + enforcement en las superficies controladas, no un sandbox
total del proceso.

### M6 — Extensión de fuentes

Para v0.8: `registro del proyecto → módulo:callable → importlib → ejecución en proceso →
SourceObservation`.

Congelado:

- el registro pertenece al proyecto, está versionado en git, **no** contiene secretos y **no** es un
  archivo administrado por Harmessi (por eso una customización válida no produce `HARMESSI-DRIFT`);
- el adapter vive en el código del proyecto y corre en el `.venv` del proyecto;
- las dependencias específicas son responsabilidad del proyecto; Harmessi no instala drivers ni
  dependencias del adapter;
- un error o fallo de import del adapter se reporta como `technical_error`;
- el hash del código del adapter forma parte de `SourceProvenance`;
- Doctor valida el registro estáticamente y no importa ni ejecuta código del proyecto;
- formato neutral estable: `adapter → SourceObservation` serializable en JSON;
- la alternativa futura (comando externo → JSON por stdout) queda conceptualmente compatible pero
  **fuera de v0.8**; los entry-points de paquetes no se implementan; no hay catálogo de conectores;
  no se agregan al core PostgreSQL, SQL Server, Snowflake, BigQuery, pandas, SQLAlchemy ni similares.

SDD: ubicación y nombre del registro, firma exacta del contrato de adapter, resolución de
`sys.path`, timeout y taxonomía de errores.

## Riesgos de scope creep

- **Catálogo de conectores por la puerta de atrás:** "ya que estamos, un adapter Postgres". Regla: el
  único adapter incluido es el de archivo (compatibilidad); los demás son del proyecto o ejemplos
  genéricos en fixtures.
- **SQL en el core:** una faceta o pedido que acepte texto de consulta. Regla: el pedido de
  observación no contiene consultas.
- **Facetas como biblioteca estadística:** la lista de facetas crece hasta reemplazar un profiler.
  Regla: solo facetas que un contrato v0.7 pueda consumir.
- **SDK/generador/sandbox de adapters:** herramientas para "facilitar" adapters. Fuera de alcance.
- **Upgrade convertido en gestor de paquetes:** el upgrade se limita a v0.7 → v0.8, plan-first.
- **"Carta de autonomía" convertida en motor de workflows:** solo si el audit del Change 0
  demuestra que la propuesta SDD no alcanza (M3) se admite un artefacto nuevo, mínimo y declarativo.
- **Supervised como segunda arquitectura:** cualquier rama de código específica de un modo fuera de
  la tabla de política es una violación de la decisión 2.
- **Ejecución que crece a orquestador:** scheduling, colas, paralelismo, remoto.
- **Write a fuentes "porque el cliente lo pide":** `write` se queda como vocabulario reservado
  deny-by-default.
- **Refactor de `ds_profile`:** cualquier cambio a su schema o CLI es STOP.

## Deuda que v0.8 no debe crear

- una segunda tabla de constantes/códigos: registro único para `SOURCE-*` y códigos de política

  nuevos siguen un único estilo, definido en SDD;

- lógica de decisión mezclada con lectura de stdin en cualquier hook nuevo (deuda 1 de §4): si se
  agrega un hook, su decisión vive en un módulo core con una función pura.
