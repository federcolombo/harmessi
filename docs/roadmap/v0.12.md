# Harmessi v0.12 — Data Scientist Experience & Composable Skills

## Estado

**EN DESARROLLO** en `v0.12-dev` (solo local). Roadmap congelado por Change 0 `20261021-v012-roadmap-and-dx-skills-audit` (2026-10-21), sobre
`main` == `origin/main` == `917339f` (`v0.11.0` publicada). Cada Change refina sus criterios en su propio SDD.

## Objetivo

Que Harmessi ayude mejor al Data Scientist a formular problemas, diagnosticar fallos, diseñar cambios coherentes con una codebase y seleccionar/componer
metodología contextual, **sin roles nuevos ni mega-agents**.

> Stable roles, small contextual skills, governed execution.

## Principios

- Role ≠ Skill ≠ Runtime. Una skill es markdown bajo demanda, sin permisos, hooks ni ejecución (foundation v0.10, sin cambios).
- Precedencia: governance/runtime > contrato del rol > contrato del proyecto > guidance de skill.
- Una skill no se convierte en agente; no se crea registry, resolver de dependencias, grafo, marketplace ni runtime de plugins.
- Lo determinista lo hace cumplir el binario (barato, estructural); la calidad metodológica sigue siendo review/evidencia. Evals ≠ tests.
- Se preservan sin reabrir: un ROL writer con N instancias de ownership disjunto; Lead no es writer; reviewer read-only; T0/T1; scope amendments;
  guardrails readopt; `domain-modeling`; `GLOSSARY.md` project-owned; recovery y upgrade de v0.11.

### Change 1 — Harness Surfaces & Skill Composition Boundaries
**Objetivo.** Formalizar qué puede evolucionar metodológicamente y qué no.
**Modelo.** *Protected* (guardrails, permisos, approval semantics, trust model, scope enforcement, límites de seguridad, enforcement determinista: `tools/**`,
hooks, `guardrails.json`, `settings.json`, contratos de rol `.claude/agents/*.md`, `SKILL.md` del Lead, documentación de proceso/runtime `sdd.md`,
`verificador.md`, `decision-ledger.md`); *Optimizable* (skills metodológicas, guidance de metodología, plantillas de razonamiento: `skills/*.md`,
`methodology.md`, `eda.md`, `kdd.md`); *Project-owned* (`GLOSSARY.md`, definiciones de negocio, Data Contracts, configuración y artefactos del proyecto).
**Scope.** Documentar el modelo (`ARCHITECTURE.md`, `methodology.md`, `SKILL.md` + plantillas espejo); derivar la superficie desde la ruta
(función pura en `skill_contract.py`, sin metadata nueva) y usarla en una validación estructural barata: un `artifacts` de skill que apunta a una
superficie *Protected* se reporta (`SKILL-ARTIFACT-SUPERFICIE-PROTEGIDA`).
**Boundaries.** Sin optimizer, runtime auto-modificable, candidate/probe engine, marketplace ni policy engine; sin campos de frontmatter nuevos.
**Dependencias.** Ninguna (tras 0). **Aceptación.** (a) las tres superficies definidas y mapeadas a rutas reales; (b) la validación detecta artifacts
protegidos y no da falsos positivos sobre `GLOSSARY.md` ni sobre rutas project-owned; (c) el contrato de skill sigue aceptando `domain-modeling`;
(d) docs y plantillas espejo en paridad. **Riesgos.** Clasificar mal un archivo → el mapeo es explícito y testeado contra el árbol real.

### Change 2 — Problem Framing / Grill-Me
**Skill** `problem-framing` (nombre confirmado por la auditoría), pequeña, con `grill-me` como **modo/patrón interno**, no otra skill.
**Contenido.** Elementos a explicitar: objetivo, decisión a soportar, unidad de análisis, población, target, restricciones, criterios de éxito, evidencia,
incógnitas, supuestos, ambigüedades materiales. Tres niveles: inferible/técnica (el Lead decide y sigue), ambigua no material (supuesto explícito y
trazable), material (checkpoint humano; semántica/negocio → `domain-modeling`). Grill-me solo si el humano pide desafiar la definición: contradicciones,
casos límite, métricas proxy, leakage conceptual, población incorrecta, éxito mal definido, requisitos incompatibles. No es interrogatorio obligatorio.
**Scope.** `skills/problem-framing.md` + plantilla espejo no aplica (la skill se distribuye por el manifest como archivo managed); manifest, Doctor
(`_ARCHIVOS_SKILL_ESPERADOS`), `SKILL.md` + plantilla, tests, docs. **Boundaries.** No duplica GLOSSARY ni Decision Ledger; sin frontmatter nuevo; no
concede autoridad. **Dependencias.** 1. **Aceptación.** contrato válido; manifest/Doctor/instalación incluyen la skill; la skill distingue los tres
niveles; grill-me explícitamente opt-in; referencia (no copia) a `domain-modeling` y ledger.

### Change 3 — Diagnosing Bugs
**Skill** `diagnosing-bugs`. Workflow: reproduce → minimize → classify → hypothesis → instrument → test hypothesis → fix root cause → regression test →
verify. Clases: code bug, data issue, environment, configuration, contract mismatch, expected behavior, nondeterminism. Exige separar síntoma de causa
raíz. **Baseline-aware:** ante un fallo durante un Change y duda razonable, evaluar el baseline de forma **focalizada** (nunca masiva) y clasificar
`introduced | pre-existing | environment | inconclusive`. **Boundaries.** Sin debugger propio; no reemplaza tests ni reviewer; no cambia topes de
remediation. **Dependencias.** 1. **Aceptación.** análoga a Change 2 + el workflow completo y la clasificación baseline presentes y verificables
por estructura.

### Change 4 — Codebase Design
**Skill** `codebase-design`. Antes de un cambio estructural razonar sobre: boundaries, ownership de módulos, acoplamiento, cohesión, primitivas
existentes, contrato público/interno, dirección de dependencias, impact radius (vía `ds_guard impact`), compatibilidad, migración, test seams.
Preferencia: reusar primitiva existente > extender > primitiva local nueva > subsistema/framework nuevo. Evita duplicación, wrappers innecesarios,
framework creep, abstracciones sin consumidor. **Boundaries.** Asesora; no decide permisos ni runtime. **Dependencias.** 1. **Aceptación.** análoga.

### Change 5 — Skill Selection, Composition & Traceability
**Objetivo.** Hacer observable cuándo el Lead usa skills, sin runtime nuevo. Tabla de selección (problema ambiguo → `problem-framing`; concepto de
negocio → `domain-modeling`; bug → `diagnosing-bugs`; cambio estructural → `codebase-design`), cargar solo las pertinentes (menos contexto/tokens),
composición simple por pares (`problem-framing`+`domain-modeling`, `diagnosing-bugs`+`codebase-design`), conflicto entre skills resuelto
semánticamente por el Lead sin violar capas superiores (ver D2), traza solo cuando la skill **influye materialmente**.
**Scope.** `SKILL.md`, `methodology.md` §28, `sdd.md`, `templates/tasks.md`, `ARCHITECTURE.md` + plantillas espejo; tests de contrato; mejora estructural
mínima de la traza solo si la auditoría de este Change la justifica. **Boundaries.** Sin resolver de dependencias, grafo, registry, marketplace ni
plugins dinámicos; `## Skills cargados` sigue siendo markdown validado. **Dependencias.** 2, 3, 4. **Aceptación.** reglas de selección,
composición, conflicto y traza documentadas y testeadas por estructura; la foundation v0.10 (sin permisos/hooks/ejecución) intacta.

### Change 6 — Release Hardening + Realistic DS Dogfooding
Sin features. Versión `0.12.0`, notas `docs/releases/v0.12.0.md` (inglés), baseline managed, manifest, installer, Doctor, smoke, regresión completa por
batches seriales (P=1), fresh install y upgrade público `v0.11.0 → v0.12.0` con artefactos project-owned preservados, privacidad. Dogfooding con
fixtures sintéticos genéricos: A framing, B framing→domain-modeling, C debugging→regression test, D architecture, E composición de 2 skills sin
cargar las otras. Los dogfoods registran observaciones cualitativas; los tests validan contrato/estructura/determinismo (evals ≠ tests).

## Decisiones de Change 0

- **D1 — Nombre `problem-framing`.** Se mantiene; no existe skill ni mecanismo equivalente (auditado).

- **D4 — Traza existente.** `## Skills cargados` ya existe y se valida; Change 5 refina el criterio («materialmente») y no crea telemetría.
