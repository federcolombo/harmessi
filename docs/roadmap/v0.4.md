# Harmessi v0.4 — Enforceable DS Quality & Controlled Change

## Objetivo

Pasar de la metodología gobernada de v0.3 a una capa donde Harmessi pueda verificar calidad científica, anticipar impacto, limitar alcance de cambios y reducir trabajo innecesario de agentes.

## Estado

- [x] Change 0 — `kdd-enforceable-checks`
- [x] Change 1 — `impact-preflight`
- [x] Change 2 — `scope-and-change-isolation`
- [x] Change 3 — `portable-core`
- [ ] Change 4 — `agent-efficiency-and-token-governance`
- [ ] Change 5 — `v0.4-release-hardening`

## Change 0 — kdd-enforceable-checks

**Estado:** DONE.

Objetivo:
- checks científicos deterministas;
- cutoff temporal;
- holdout;
- leakage determinista básico;
- baseline cuando aplica;
- integración con checks/status/Lead.

Principios:
- `PASS/WARN/FAIL/N/A`;
- nunca `PASS` por desconocimiento;
- leakage semántico sigue siendo responsabilidad del Lead/metodólogo;
- baseline existence ≠ baseline quality;
- no modificar todavía readiness/promotion.

## Change 1 — impact-preflight

**Estado:** DONE.

Objetivo: detectar consumidores **potencialmente afectados** antes de ejecutar.

Componente: `tools/dsimpact/`

Debe detectar de forma estática y determinista, cuando sea posible:
- archivos modificados;
- funciones/clases/constantes Python;
- imports y referencias;
- feature/column lists;
- asserts;
- expected lists;
- validators;
- configs;
- notebooks;
- referencias a archivos eliminados/renombrados.

Regla central: `finding = potentially affected`.

Nunca afirmar automáticamente que un consumidor está roto.

No incluir:
- ejecución;
- auto-fix;
- LLM scanner;
- dependency graph persistente;
- tree-sitter;
- lenguaje universal.

Salida humana + JSON determinista.

## Change 2 — scope-and-change-isolation

**Estado:** DONE.

Objetivo: comparar el alcance declarado de un Change con el diff real.

Debe permitir expresar un scope mínimo y verificar:
- archivos permitidos;
- archivos realmente modificados;
- modificaciones fuera de scope;
- expansión accidental;
- cambios encadenados no declarados cuando sean detectables.

Principio: `scope declarado ↔ git diff real`.

No crear:
- sandbox filesystem;
- merge inteligente;
- sistema de permisos genérico;
- graph de dependencias.

Integrar con SDD y bounded autonomy.

## Change 3 — portable-core

**Estado:** DONE (alcance mínimo, decisión explícita del usuario tras STOP por cambio arquitectónico
material: sin reestructuración física de archivos — ver `ARCHITECTURE.md` y
`openspec/changes/20260916-portable-core/`). Entregado: inventario core/adapter formal en
`ARCHITECTURE.md`, reglas de dependencia, 5 items de deuda concreta identificados (incluye el
eager-import de `ds_guard.py` y los dos archivos "mixtos" sin separar,
`hook_presupuesto.py`/`hook_validar_comando.py` y `launcher_common.py`), tests estructurales
(`tools/tests/test_architecture_boundaries.py`) que fallan ante un acoplamiento core→adapter nuevo
(verificado con una inyección de prueba). La reestructuración física queda registrada como deuda
para un change futuro cuando exista necesidad real (multi-provider).

Objetivo: reducir acoplamiento entre el core de Harmessi y Claude Code.

Atacar la deuda detectada en v0.3:
- runtime Python demasiado completo incluso en discovery;
- imports globales;
- hooks/adapters Claude acoplados al core.

Dirección:
- core neutral;
- contratos portables;
- lazy/modular imports cuando corresponda;
- separación clara entre core y adapter Claude;
- preparar futuros adapters sin implementarlos todavía.

No implementar todavía:
- Codex/Gemini/Grok;
- routing;
- fallback multi-provider.

## Change 4 — agent-efficiency-and-token-governance

Objetivo: hacer observable y gobernable el costo operativo de los agentes.

Señales candidatas:
- agentes lanzados;
- rol;
- task-id;
- resumes;
- duración;
- resultado;
- ciclos writer/reviewer;
- tareas duplicadas;
- retry sin finding nuevo;
- fork sin output;
- auditorías redundantes.

Debe detectar patrones como:
- no-op/wait agents;
- demasiadas delegaciones;
- repetición innecesaria;
- bounded remediation excedida.

No implementar:
- billing exacto;
- token accounting inventado;
- optimizador autónomo complejo;
- provider-specific telemetry como core.

## Change 5 — v0.4-release-hardening

Sin features nuevas.

Gate de release:
- versión consistente;
- suites completas;
- scratch installs;
- smoke de los componentes nuevos;
- backward compatibility;
- privacidad/portabilidad;
- docs/release notes;
- reviewer transversal;
- regeneración final de `control.json`;
- Doctor sin `ERROR`.

Mejoras no bloqueantes → deuda v0.5.

Resultado final:
`READY FOR v0.4.0 RELEASE` o `NOT READY`.
