# Harmessi v0.11.0 — Operational Robustness & Recovery

v0.11 strengthens how the harness actually behaves before adding new Data Science feature families. It is not a feature release.
Principle: **Fail explicitly, recover deterministically, preserve evidence.** Harmessi governs evidence; it does not generate it.

## What's included

### Git and scope fail closed
- An unknown Git state is never treated as a clean state. A failing Git command, an invalid or deleted ref, a missing Git, or malformed output
  produces the governed finding `ALCANCE-GIT-ILEGIBLE` instead of an empty list of touched files.
- Rename: both sides are evaluated (a rename from an unauthorized path is reported); copy: destination only. Refs are validated so a ref starting with `-`
  is not read as an option; Git output is captured as bytes so a `\r` in a file name is preserved (that one test is skipped on Windows and
  verified there with a mocked subprocess).
- `ds_guard` status, validate, archive, init and notebook-diff exit with code 3 when Git fails. `init` on a repository without commits also
  exits 3, intentionally.
- The codes are documented in the verifier role and its template.

### Decision ledger: corrections and integrity
- `ds_guard decision correct` appends a correction to an existing decision without rewriting history: previous lines stay byte-identical.
  `list` and `show` display the effective value and its history. `correct` does not change the meaning of a decision (use `supersede`).
- `ds_guard decision verify` checks integrity: sequence continuity, duplicate ids, dangling references, and the `prev_hash` chain.
- New entries carry a `prev_hash` chain (`schema_version` 2). Legacy v0.10 ledgers read without migration.
- This is tamper-evidence against naive edits, not authenticity. See Known limitations.

### Sessions, continuations and recovery
- The session default stays at 90 minutes, now defined in a single constant (`SESSION_MINUTES_DEFAULT`); `maxTurns` is unchanged.
- An early warning `AVISO-SESION-POR-VENCER` (stderr, 10 minutes or less) is emitted, and `session status` reports remaining minutes.
- `session start --retomar` resumes from the last closed session: it inherits counters and the `max_*` limits, so an expired session does
  not mean lost work. `max_sessions` and the aggregate-minutes limit still apply.

### Parallel Change isolation (4B)
- A path outside a Change's own scope is classified against the other open Changes: no owner keeps `ALCANCE-RUTA`; a single owner yields the
  informational `ALCANCE-ATRIBUIDA-OTRO-CHANGE`; a double owner (or own plus foreign) yields `ALCANCE-CONFLICTO-CHANGES`; a foreign active
  Change whose scope cannot be verified yields `ALCANCE-OTRO-CHANGE-INVALIDO`. The last two block.
- A foreign Change counts only if, at the baseline commit of the current Change, it has an active state, all required artifacts approved, and
  an unchanged `scope_hash`. Catch-all, invalid, or `.claude/` patterns are discarded. Attribution never widens the Change's own scope.
- The attribution is honest, not authenticated: it raises the cost of evasion, it does not make it impossible.
- 4A (runtime attribution) did not ship: no real hook payload evidence was obtained, so **H1 remains UNCONFIRMED** and the hook was not changed.

### Upgrade, recover and install resilience
- `ds_init upgrade` and `ds_init recover` are transactional and dry-run by default. A persistent journal records phases. A failure rolls back
  to the previous state; it does not roll forward. A cooperative file lock prevents concurrent runs. `recover --forzar` proceeds despite user
  edits after an interruption and keeps a `.recover-bak` copy.
- `.ds_init/control.json` is written atomically. A generic manifest completeness test fails when a runtime module is missing from the manifest,
  and manifest parity now also checks the inverse direction.
- Doctor: `HARMESSI-VERSION` gives an actionable remedy, and `HARMESSI-MIGRACION` detects an interrupted upgrade or install.
- Project-owned data (guardrails customizations, amendments, `GLOSSARY.md`, ledger, approvals, Cards, Data Contracts) is preserved
  byte-identical by `upgrade`.

### Release hardening and validation evidence
- Version `0.11.0`, these notes, and a release smoke test.
- Dogfooding: a project installed from a checkout of the public tag `v0.10.0` plus synthetic project-owned state was upgraded with `upgrade`
  (dry run, then `--execute`): 13 managed files updated, project-owned files byte-identical, and the second run idempotent.
- A hard interruption (process killed mid-run) was detected by Doctor, `recover` restored the previous state, and `upgrade` then converged.
- The full regression ran in sequential batches on Windows.

## Compatibility
- The new modules use only the standard library; no new third-party dependencies.
- The 90-minute session default and `maxTurns` are unchanged.
- The supported upgrade origin is the public tag `v0.10.0`. `migrate-hashes` remains available.

## Known limitations
- Approvals and ledger authorship are T0 / `declared`; `console_confirmed` is an interactive-presence signal, not proof of identity.
- Ledger integrity is tamper-evidence only, not authenticity: the legacy prefix (except its last line) is not protected, deleting the tail is
  not detected, and writes are read-modify-write without a lock (concurrent writers can lose an entry). A legacy ledger that is inconsistent
  blocks writes until fixed by hand.
- Parallel-Change attribution depends on approvals stored in `control.json`, which anyone with the repository can edit. A foreign Change
  approved after the baseline of the current Change does not attribute (fail closed). Broad but non-catch-all foreign patterns can attribute
  paths of the harness itself.
- H1 (hook payload fields) is unconfirmed; a relaunched `Agent` with the same id resets its continuation counter.
- The upgrade lock is cooperative and has no pid detection: a hard kill can leave `.ds_init/lock`, which is removed by hand.
- No downgrade and no migration of project data. `upgrade` does not recreate a managed file deleted by hand and does not adopt drift.
- Doctor runs from the Harmessi checkout, not from the installed project.
- The last fix of the parallel-Change work (state and approval read from the baseline snapshot) did not go through an independent review, and
  the `transition` and `archive` gates are covered at function level, not through the full CLI.
- The session clock is still wall-clock: waiting for a human or for long tests consumes the session. This is mitigated by the early warning and
  `--retomar`; the clock is not paused.
- A lock left by a hard kill is removed by hand.
- Unit fixtures are synthetic. The regression ran in sequential batches on Windows; no real POSIX or macOS host was validated.
- `tools/dsimpact/git_source.py` keeps its fail-open content reads (deferred debt).

## Upgrading
1. From the Harmessi checkout, run `python -m tools.ds_init upgrade --destino <project>` as a dry run and review the output.
2. Run it again with `--execute`.
3. If a run is interrupted, run `python -m tools.ds_init recover --destino <project>` (dry run first, then `--execute`), then repeat `upgrade`.
4. `migrate-hashes` is still available for the managed-hash baseline.
