# Harmessi v0.14.0 — Evidence-Driven Harness Improvement

v0.14 lets Harmessi propose variants of Optimizable harness surfaces, run them in isolation against a baseline using the v0.13 evaluation
foundation, keep the evidence, and produce a promotion proposal. The principle is `Propose → Probe → Compare → Governed Promotion`: an LLM or a
human proposes, the runtime executes and measures, the evaluation compares evidence, and governance decides whether anything may be adopted.
There are no new roles, permissions or hooks. The package adds no telemetry or phone-home; running a probe or cycle against a real provider
uses that provider (prompts and guidance go to the provider you choose). No probe was run against a real provider during this release: the
dogfood uses a scripted fake adapter that is deterministic, validates the evidence, decision and governance pipeline, and does not measure
the real quality of any skill. A successful `aplicar_promocion` and the CLI are covered by the tests in `tools/harmessi_improve/tests`.

v0.14 produces evidence and governed proposals. It does NOT silently modify the harness, and nothing is promoted without explicit governance.

## What's included

### Candidate model & isolation
- A versioned `Candidate` contract (`tools/harmessi_improve/candidate.py`): `candidate.json` plus `content.md` under
  `.harmessi/improvement/candidates/<candidate_id>/`, with a reproducible id derived from the base path, the base hash and the content hash.
- Structural rejection: only Optimizable surfaces can be the base of a candidate. Protected surfaces (including `tools/harmessi_improve/`
  itself) and project-owned files are rejected before anything runs, fail-closed. A candidate cannot derive from another candidate.
- A heuristic privacy scan of candidate text (secrets, emails, user paths) reusing the redaction of `harmessi_bench`.
- A state machine `proposed → evaluated → promotable | rejected | inconclusive`, where every state has a consumer.

### Probe
- A baseline-versus-candidate execution with the same adapter, suite, target, seed, evaluator and repetitions; the only difference is the guidance
  injected through an adapter wrapper. It consumes the v0.13 runner, `save_run` and run manifest; there is no second evaluation runtime.
- A frozen policy (primary criterion, optional secondary, tie policy, repetitions, instability threshold) is hashed and recorded in `probe.json`
  before results are seen. Failures are classified (`candidate_failure`, `baseline_failure`, `environment_failure`, `inconclusive`) and an
  environment failure is never read as "the candidate is worse". An incompatible resume is rejected.

### Evidence comparison & decisions
- A decision is recomputed from the real `result.json` files and the frozen policy, and the verdict is delegated to `compare_runs`
  (`candidate_better`, `baseline_better`, `equivalent`, `inconclusive`). An edited `probe.json` or declarative metadata cannot change it.
- Anti cherry-picking: criteria are frozen per candidate, a new probe requires a prior decision, a minimum sample size applies, and unstable
  repetitions of the candidate count as a regression.
- `decision.json` is the only path to `evaluated`, `promotable`, `rejected` or `inconclusive`. A candidate is never `promotable` because its
  metadata or its proposer says it is better.

### Governed promotion
- A promotion proposal with the diff, the evidence, the hashes and the decision. Applying it is fail-closed: the active surface hash must still
  equal the base hash, and a normal Change in implementation with `console_confirmed` (T1) approvals is required. Advance authorization (T0)
  is not enough. A stale base is rejected, and a write-ahead record makes an interrupted apply recoverable.
- Evaluation is not release verification: an adopted promotion is a normal Change with its own tests, review and approvals. This release did
  not promote any real candidate.

### Evidence-backed lessons
- A bounded, structured `lesson.json` with verifiable `evidence_refs`, declared applicability, and states `hypothesis`, `evidence-backed` and
  `deprecated`. Lessons are created only through an explicit flow tied to an open Change, never by a normal run, and are reused only when the
  applicability matches and the evidence is still current. A privacy scan covers project glossary terms. There is no cross-project library.

### Improvement budgets & bounded cycle
- Budgets with conservative defaults and hard ceilings that no configuration can exceed (candidates, probe cycles, runs per candidate, retries,
  wall clock). The state is persisted with a file lock and verified on load.
- A bounded improvement cycle, with no nesting and no recursion: the engine does not optimize itself.

### CLI
- `python -m tools.harmessi_improve` with `budget`, `candidate`, `probe`, `decide`, `promote`, `lesson` and `cycle`. It delegates to the package
  API without extra rules. Exit codes: 0 ok (including a cycle stopped by an exhausted budget), 1 rule or gate rejection, 2 invalid usage,
  3 unexpected environment error. Error messages carry no absolute repository paths or tracebacks.

### Release hardening
- Version `0.14.0`, these notes, a release smoke test, and a deterministic dogfood of the full flow on a temporary repository with a copy of a
  skill (the real skill is not modified). The contract inventory gains the new CLI and the versioned contracts, all classified `experimental`.
  The portability workflow adds the lightweight new tests and moves to newer major versions of the checkout and setup-python actions.

## What v0.14 does NOT do
- No silent self-modification: every candidate is written under `.harmessi/improvement/`, never over an active surface.
- No automatic promotion: promotion needs a recomputed decision, a normal Change and T1 approvals.
- No Protected surfaces: Protected paths never enter the improvement engine, and the engine itself is Protected.
- No governance bypass: roles, permissions, hooks, settings and guardrails are unchanged.
- No engine self-improvement: there is no meta-loop and no unbounded recursion.
- No telemetry and no network access in the package.

## Inspiration
The design is conceptually inspired by the idea of recursive harness improvement (propose a variant, test it, keep what the evidence supports).
It has no dependency on any external project, service or library, and it adopts no external code.

## Compatibility and upgrading
- Standard library only; no new third-party dependencies.
- `tools/harmessi_improve/` is checkout-only (like `tools/harmessi_bench/`): `ds_init` does not install it, and installed projects receive no
  `.harmessi/improvement` directory, candidates or lessons.
- Roles, permissions and hooks are unchanged; `maxTurns` is unchanged for every agent.
- The supported upgrade origin is the public tag `v0.13.0`: `python -m tools.ds_init upgrade` (dry run by default) updates managed files and
  preserves project-owned files (edited `CLAUDE.md`, `GLOSSARY.md`, data, notebooks, notes, approvals, ledger, amendments, project skills).

Steps:
1. From the Harmessi checkout, run `python -m tools.ds_init upgrade --destino <project>` as a dry run and review the output.
2. Run it again with `--execute`.
3. If a run is interrupted, run `python -m tools.ds_init recover --destino <project>` (dry run first, then `--execute`), then repeat `upgrade`.

## Known limitations
- Evals remain deterministic text proxies: shallow scorers, no LLM-as-judge, and a weak signal for subtle quality differences. A verdict
  measures the proxy, not the real quality of a skill.
- `duration_s` is not used to decide (it is not deterministic); tokens, cost, retries and STOP are not supported as comparison dimensions.
- Provenance is not cryptographic: the internal consistency of `.harmessi/improvement` and `.harmessi/evals` does not prove who wrote the files.
- The privacy scan is heuristic: free text within the length limit may still carry content that the redaction does not detect.
- Only Windows was used as an execution host. Linux/macOS not validated by execution; only contracts and CI configuration exist for them.
- The portability workflow now lists the new tests, but remote CI execution not observed during release. Remote portability CI pending observation.
- The repository path is sanitized in the CLI output and the package's own artifacts carry no absolute paths, but operating-system error
  texts may include them.
- The updated CI actions (checkout v5, setup-python v6) are inferred to be compatible, not observed.
- Providers reach at most `contract-tested`; no provider is `live-validated` and live use remains opt-in.
- The new contracts (candidate, probe, decision, proposal, lesson, budget state, policy) are versioned and classified `experimental`; they have no
  dedicated compatibility window yet. v1.0 is not declared.
- Resume of two simultaneous runs of the same probe is not mutually blocked during execution, a probe that dies between budget consumption and
  writing `probe.json` is not recoverable, and the stale-lock restoration is best-effort.
- Promotion: the scope anchored by hash and amendments was not exercised, there is no automatic Decision Ledger entry (only suggested text),
  and the managed baseline is updated by the release, not by the promotion.
- Carried over: H1 (hook payload fields) remains UNCONFIRMED; the skill trace is cooperative; the improvement package is checkout-only.
- GitHub Release UI pending (`gh` unavailable during release).
