# Harmessi v0.13.0 — Portability, Evaluation & Contract Hardening

v0.13 builds the primitives needed to compare a harness baseline against a candidate with deterministic evidence, makes those runs reproducible,
declares provider and adapter support levels honestly, hardens portability and fail-closed behavior, and inventories the contracts third parties
may consume. There are no new roles, permissions or hooks.

v0.13 enables evidence-based comparison but does NOT automatically improve or promote harness changes.

## What's included

### Evaluation & benchmark foundation
- Extends the existing `tools/harmessi_bench` (no parallel package). Cases carry a `case_contract_version`, optional fixtures and a
  `surface_under_test`; legacy unversioned cases and results are still read.
- Suites: a deterministic manifest (`suite_id`, `suite_version`, case ids, canonical `suite_hash`) with a human- and machine-readable summary
  (`--suite`, `suite-check`). `result.json` carries `schema_version`, `evaluator_version` and the suite block.
- A deterministic four-state verdict for baseline versus candidate: `candidate_better`, `baseline_better`, `equivalent` and `inconclusive`.
  It is conservative: unavailable evidence, different case sets or a different evaluator yield `inconclusive`. There is no LLM-as-judge scorer.
- A public synthetic suite, `harmessi-core-synthetic`, with 9 generic cases (framing, debugging, domain modeling, codebase design, recovery and
  tool contracts).
- Surface boundary: only Optimizable surfaces can be the subject of a comparison; Protected surfaces have no promotion mechanism here.

### Reproducible harness runs
- A versioned run manifest inside `result.json`: Harmessi version, commit and cleanliness (`unknown`/`null` when Git is not reliable), hashes of
  skills, surfaces and guardrails, provider/model/effort, evaluator, suite and cases, informative seed, minimal platform, and an `identity_hash`
  computed over material fields only.
- Best-effort redaction of user paths, emails and tokens in persisted excerpts and score details.
- Safe resume: an incompatible `--resume` is rejected without touching the existing result, and an existing `run_id` with a manifest is
  protected. Result writes are atomic (temporary file plus replace).
- Three documented levels: configuration reproducibility, execution determinism (scorers and comparison only) and stochastic results (LLMs).
  There is no bit-for-bit promise for model output.
- `compare` reports a `config_diff` and applies comparability rules based on the manifests.

### Provider & adapter conformance
- Providers (`claude_code`, `codex`, `gemini`, `grok`): `tools/providers/conformance.py` checks executable detection, version parsing, the
  invocation contract, config shape and failure behavior without credentials. All four are `contract-tested`. A provider is
  `locally-smoke-tested` only when the opt-in smoke is run with `HARMESSI_SMOKE_LOCAL=1`. Live checks are opt-in (double opt-in) and not
  validated; no provider is `live-validated`.
- Source observers: `tools/datasources/conformance.py` (installed) offers `verificar_observer`, with a report that marks evidence as real or
  fixture.

### Portability
- `dsimpact` is fail-closed: unknown evidence is no longer treated as empty. Unanalyzed consumers and changed files are listed visibly in the
  summary and the CLI, and an inconclusive result is reported as such.
- New validation finding `SKILL-TRAZA-SECCION-DUPLICADA` when a `tasks.md` has two `## Skills cargados` sections (no automatic merge).
- Safe console output (`errors="replace"`) in the new CLIs, and `docs/portability.md` with the audit and inherited debts.
- Portability tests exercised on the Windows host (spaces, Unicode, CRLF/LF, temp dirs, subprocess, Git in a temporary repository).
- A `portability-smoke` GitHub Actions workflow is present and structurally validated; its remote execution was not observed.

### Contracts, compatibility and deprecation
- `docs/contracts/inventory.json` (with a README): a classified inventory (`public-candidate`, `internal`, `experimental`) anchored to the code
  by tests. It is an inventory, not a promise of stability, and v1.0 is not declared.
- `docs/versioning.md`: how 0.x and 1.x are read, and a compatibility window of the current version plus the two previous minors (older
  artifacts are read on a best-effort basis).
- `docs/deprecation.md` and a minimal primitive, `tools/harmessi/deprecation.py` (mark, warning, replacement, earliest removal version); the
  registry is empty.

### Release hardening
- Version `0.13.0`, these notes and a release smoke test. The managed-file baseline was regenerated once for the release. Validation evidence
  is recorded in the Change verification file.

## Compatibility and upgrading
- Standard library only; no new third-party dependencies.
- Roles, permissions and hooks are unchanged, checked by a diff against the tag `v0.12.0` over the agent contracts, `settings.json`,
  `guardrails.json` and the hooks launcher. `maxTurns` is unchanged for every agent.
- New finding: `ds_guard validate` now reports `SKILL-TRAZA-SECCION-DUPLICADA` if a trace in `tasks.md` has two `## Skills cargados` sections.
  Installed projects with such a duplication will see it after upgrading. In this repository no existing Change had one.
- The supported upgrade origin is the public tag `v0.12.0`: `python -m tools.ds_init upgrade` (dry run by default) updates managed files and
  preserves project-owned files (edited `CLAUDE.md`, `GLOSSARY.md`, data, notes, approvals, ledger, amendments, project skills).
- `datasources/conformance.py` is a new installed module.

Steps:
1. From the Harmessi checkout, run `python -m tools.ds_init upgrade --destino <project>` as a dry run and review the output.
2. Run it again with `--execute`.
3. If a run is interrupted, run `python -m tools.ds_init recover --destino <project>` (dry run first, then `--execute`), then repeat `upgrade`.

## Known limitations
- Deterministic evals are a text proxy, not a semantic measurement: shallow scorers, a single sample per case, no statistical thresholds, no
  LLM-as-judge and no leaderboard. The public suite is weak against prompt echo.
- Only Windows was used as an execution host. Linux and macOS are covered by contracts, tests and CI configuration, not by execution.
- The CI workflow was validated structurally; remote execution was not observed during the release.
- Providers reach at most `contract-tested`; conformance against test doubles does not guarantee the behavior of the real CLI. Live use is
  opt-in and not validated. The secret check is heuristic and the "installs nothing" check is a module-level import scan, not exhaustive.
- Reproducibility: single writer per `run_id`; redaction is best-effort (short unquoted values, non-string values and `/users/` in URLs);
  `commit` is informative and the seed is not guaranteed by the provider; a few edge cases remain (Windows reserved `run_id` names, corrupt
  existing results).
- `dsimpact`: notebook cells with magics are ignored without a signal, the CLI exits 0 even on an inconclusive result, and a `parse_error`
  can be printed alongside "no consumer". The portability audit of inherited modules is pending (marked as debt in `docs/portability.md`).
- Contract inventory: exit codes are observed, not guaranteed; the code evidence checks are lenient shortcuts, sub-subcommands are not
  inventoried, and the compatibility fixtures are hand-derived rather than extracted from the tags.
- Carried over: H1 (hook payload fields) remains UNCONFIRMED; per-instance ownership for N writers is not implemented; the skill trace is
  cooperative.
- GitHub Release UI may be pending if `gh` is unavailable.

## Deferred to v0.14+
Direction only, without a contract: v0.14 (evidence-driven harness improvement). See `docs/roadmap/v0.13.md`.
- Not implemented in v0.13 and deferred: automatic candidate generation, recursive improvement, automatic promotion, improvement budgets.
- Not implemented in v0.13 and deferred: a cross-project library of lessons, columnar `ds_profile`, as-of Cards, T2 provider security.
- Not part of the product: a marketplace, a SaaS or a GUI.
