# Harmessi v0.12.0 — Data Scientist Experience & Composable Skills

v0.12 helps the Data Scientist frame problems, diagnose failures, design changes that fit a codebase, and have the Lead select and compose
methodology in context. It is mostly guidance (three new skills and selection rules), plus one new structural check (the surface of a skill's `artifacts` path) and a resync
of the installed `sdd.md` template: **stable roles, small contextual skills, governed execution.** There are no new roles.

## What's included

### Harness Surfaces
- The harness now names what may evolve methodologically and what may not. Three surfaces, derived from the file path (no new frontmatter
  field, no declared metadata):
  - **Protected**: guardrails, permissions, approval semantics, trust model, scope enforcement, and deterministic enforcement (`tools/**`, hooks,
    `guardrails.json`, `settings.json`, role contracts, the Lead `SKILL.md`, and process/runtime documents such as `sdd.md`, `verificador.md`
    and `decision-ledger.md`).
  - **Optimizable**: methodological skills, methodology guidance and reasoning templates (`skills/*.md`, `methodology.md`, `eda.md`, `kdd.md`).
  - **Project-owned**: `GLOSSARY.md`, business definitions, Data Contracts, and project configuration and artifacts.
- A skill whose `artifacts` points at a Protected surface is reported by `ds_guard validate` with `SKILL-ARTIFACT-SUPERFICIE-PROTEGIDA`.
  Project-owned paths such as `GLOSSARY.md` are not flagged, and `domain-modeling` remains valid.

### `problem-framing` skill
- Makes the problem explicit before work starts: objective, decision to support, unit of analysis, population, target, constraints, success
  criteria, evidence, unknowns, assumptions, and material ambiguities.
- Three levels: inferable or technical (the Lead decides and continues), ambiguous but not material (an explicit, traceable assumption), and
  material (a human checkpoint; business semantics go to `domain-modeling`).
- `grill-me` is an **opt-in mode** of the same skill, used only when the human asks to challenge the definition (contradictions, edge cases,
  proxy metrics, conceptual leakage, wrong population, ill-defined success). It is not a mandatory interrogation, and it hands validation
  questions to the methodologist.
- It references `domain-modeling` and the Decision Ledger; it does not duplicate them.

### `diagnosing-bugs` skill
- Workflow: reproduce, minimize, classify, hypothesis, instrument, test the hypothesis, fix the root cause, add a regression test, verify.
- Classes: code bug, data issue, environment, configuration, contract mismatch, expected behavior, nondeterminism. It requires separating the
  symptom from the root cause.
- **Baseline-aware attribution**: when a failure appears during a Change and there is reasonable doubt, the baseline is evaluated in a focused,
  read-only way (never a mass run) and the failure is classified as `introduced`, `pre-existing`, `environment`, or `inconclusive`.
- It does not replace tests or the reviewer, and it does not change remediation limits.

### `codebase-design` skill
- Before a structural change, reason about boundaries, module ownership, coupling, cohesion, existing primitives, public versus internal
  contract, dependency direction, impact radius (via `ds_guard impact`), compatibility, migration, and test seams.
- Preference ladder: **reuse an existing primitive > extend it > add a new local primitive > add a new subsystem or framework.**
- It warns against duplication, needless wrappers, framework creep, and abstractions without a consumer. It advises; it does not decide
  permissions or runtime behavior.

### Contextual skill composition
- Selection: an ambiguous problem points to `problem-framing`, a business concept to `domain-modeling`, a bug to `diagnosing-bugs`, a
  structural change to `codebase-design`.
- Minimal loading: the Lead loads only the pertinent skills, to spend less context.
- Simple pairs: `problem-framing` with `domain-modeling`, and `diagnosing-bugs` with `codebase-design`.
- Conflict: when two skills disagree, the Lead resolves it on the merits without violating a higher layer, and records the criterion in the
  reason of the trace entry. The precedence is unchanged: governance and runtime, then the role contract, then the project contract, then
  skill guidance. If a higher layer is involved, it wins and the standing STOPs still apply; the conflict rule never allows skipping a STOP.
  If resolving it implies a decision reserved to the human (target, features, validation, problem definition, what is discarded) or there is
  doubt whether a higher layer is involved, the Lead proposes it to the human instead of resolving it. On a tie, the more restrictive
  guidance (the one requiring a human checkpoint) prevails. There is no merge engine.
- There is no resolver, dependency graph, or registry. A skill is still on-demand markdown with no permissions, hooks, or execution.

### Traceability
- `## Skills cargados` in `tasks.md` remains validated markdown. The rule now says when to record: when a skill **materially influences** a
  decision, a design, or a diagnosis. Loading a skill that changes nothing needs no entry. There is no telemetry.

### `sdd.md` template resync
- The installed `sdd.md` template had drifted from the repository document. Installed projects now receive the same sections and amendments
  as the repository.

### Release hardening
- Version `0.12.0`, these notes, and a release smoke test. The managed-file baseline was regenerated once for the release.
- Validation (regression in sequential batches, fresh install, upgrade from the public tag, Doctor, privacy sweep, and dogfooding with
  synthetic generic fixtures) is recorded in the Change verification evidence. Dogfoods record qualitative observations; tests validate
  contract, structure, and determinism. Evals are not tests, and no evals framework ships here.

## Compatibility
- Standard library only; no new third-party dependencies.
- Roles, permissions, and hooks are unchanged. This was checked by a diff against the tag `v0.11.0` over the agent contracts, `settings.json`,
  `guardrails.json`, and the hooks launcher, which came back empty. `maxTurns` is unchanged for every agent.
- The supported upgrade origin is the public tag `v0.11.0`: `python -m tools.ds_init upgrade` (dry run by default) preserves project-owned files
  byte-identical.

## Known limitations
- Skills are guidance. Nothing enforces the quality of the reasoning they suggest; that remains review and evidence. The only deterministic
  checks are structural (contract, manifest, surface of an `artifacts` path).
- The skill trace is cooperative: it depends on the Lead recording it, and the binary validates its format and references, not its
  completeness. A duplicated `## Skills cargados` section in `tasks.md` is silently ignored (only the first occurrence is read), so the
  trace is cooperative and not complete.
- Per-instance ownership in the hook (enforcement for N writer instances) is not implemented; it depends on H1, which is UNCONFIRMED.
- The enum of decision types for the Decision Ledger is deferred.
- Only Windows was validated; no real POSIX or macOS host.
- H1 (hook payload fields) remains UNCONFIRMED.
- Deferred debts: columnar `ds_profile` reading and bytes-per-dtype; historical (as-of) Cards; a T2 provider; full cross-platform CI; public
  evals and benchmarks; and the fail-open content reads of `tools/dsimpact/git_source.py`.
- There is no optimizer, no self-improving harness, no candidate/probe engine, and no marketplace. Protected surfaces are not meant to be
  changed by the harness itself.

## Upgrading
1. From the Harmessi checkout, run `python -m tools.ds_init upgrade --destino <project>` as a dry run and review the output.
2. Run it again with `--execute`.
3. If a run is interrupted, run `python -m tools.ds_init recover --destino <project>` (dry run first, then `--execute`), then repeat `upgrade`.
